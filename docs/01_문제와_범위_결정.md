# 제가 다니는 센터에 필요한 기능부터 정했습니다

[FITORY](../README.md) / 설계 기록 1

FITORY는 제가 다니는 PT센터에서 식단·운동 기록과 트레이너의 코칭을 연결하는 서비스입니다. 출발점은 식단 기록이었습니다. 개인 카카오톡으로 식단 사진을 보내기 부담스러워하는 회원들을 위해 트레이너가 제안했습니다. 저도 그런 회원 중 하나였기에 직접 만들어 보기로 했습니다.

## 기록에서 코칭과 변화 확인까지

[첫 기획안](reference/식단관리앱_개발기획안_v1_0.md)은 회원의 기록과 트레이너의 피드백을 한 식사에 묶었습니다. 이후 개발 범위를 바꿔도 이 과정은 유지했습니다.

- **회원이 식사를 남깁니다.** 사진과 함께 먹은 시각·음식·트레이너에게 보낼 메시지를 기록합니다. 나중에 올린 식사도 구분할 수 있게 먹은 시각과 등록 시각을 따로 둡니다.
- **트레이너가 할 일을 확인합니다.** 첫 화면에서 아직 처리하지 않은 식사를 보고, 식사별로 확인·평가·답변합니다.
- **회원이 피드백을 읽습니다.** 답글은 해당 식사에 붙이고, 새 피드백을 표시합니다. 별도 채팅방을 만들지 않아도 어떤 식사에 관한 이야기인지 함께 볼 수 있습니다.

운동에서는 트레이너의 시트에 있는 계획을 가져오고, 회원이 실제로 한 세트와 중량을 기록합니다. 인바디 변화 보고서는 같은 기간의 식단·운동·체성분을 묶어 보여주며, 트레이너가 총평을 남깁니다. 계획·수행·평가를 구분해 회원과 트레이너가 같은 기록을 보고 대화하도록 했습니다.

트레이너가 식사를 열어 보기만 했다고 처리를 끝내지는 않습니다. 확인과 피드백을 남기는 동작을 두고, 이후 직접 써 보며 확인만 할 메시지와 답변할 메시지를 나눴습니다. 이 결정은 [트레이너 업무 흐름](02_트레이너_업무_흐름과_처리_규칙.md)에서 자세히 설명합니다.

## 직접 만들고 운영할 수 있는 범위로 기획했습니다

제가 다니는 센터의 트레이너와 회원들이 실제로 사용할 앱이므로, AI 도구를 활용해 직접 만들고 운영할 수 있는 범위로 기획했습니다. 첫 출시에서는 회원이 식사를 남기고 트레이너가 확인·평가·답변하는 흐름에 집중했습니다([변경 기록](../CHANGELOG.md) v1.1).

사용 형태는 링크로 전달하는 모바일 웹앱(PWA)을 택했습니다. 회원은 링크를 받아 사용하고 휴대폰 홈 화면에도 추가할 수 있습니다. 스토어 배포를 거치지 않고 센터에서 사용을 시작할 수 있는 방식입니다.

가입도 닉네임과 숫자 6자리 PIN으로 정했습니다. 이메일·전화번호를 받지 않으면서 메일 발송 서비스와 도메인 구매가 빠졌고, 담당 트레이너는 회원이 가입할 때 고르게 했습니다. 연락처를 받지 않는 가입은 이후 계정 복구 방식에도 영향을 줬습니다([가입과 계정 보안](03_가입과_계정_보안.md)).

## 현재 제품의 범위와 선택 기준

회원 화면은 식단·운동·커뮤니티·설정, 트레이너 화면은 확인·회원·커뮤니티·설정으로 나눴습니다. 회원은 자기 기록을 중심으로 움직이고, 트레이너는 처리할 일과 담당 회원을 기준으로 움직이기 때문입니다. 운동 안에서는 루틴·운동 기록·인바디를 나눠 계획과 수행, 결과를 각각 살펴봅니다.


| 선택 | 현재 범위 | 판단 기준 |
|---|---|---|
| 사용 형태 | 링크로 전달하고 홈 화면에 추가하는 모바일 웹앱 | 센터 회원이 휴대폰에서 기록하고 확인하는 흐름 |
| 가입 | 닉네임·6자리 PIN, 회원이 담당 트레이너 선택 | 연락처 없이 시작하고, 계정 복구는 본인이 수행 |
| 식단 | 사진·음식·질문, 평가와 답변 | 한 식사를 두고 기록과 피드백을 함께 확인 |
| 운동 | 시트의 루틴, 실제 수행, 이전 기록과 메모 | 기존 작성 방식을 유지하고 운동 중 입력을 줄임 |
| 변화 확인 | 같은 측정 기간의 식단·운동·체성분·총평 | 흩어진 기록을 코칭에 사용할 자료로 묶음 |
| 참여 | 추천 식단, 운동 팁, 식단·운동·중량 순위와 수상 | 기록을 이어갈 이유를 제공하고, 비교 기준과 공개 범위를 명시 |

칼로리 자동 분석·결제·별도 채팅방·센터 관리자 웹은 범위에서 제외했습니다. 트레이너와 회원이 기록을 주고받고 다음 계획을 정하는 과정에 집중합니다.

범위와 사용 방식을 구체화한 과정은 기획안 세 판에 남아 있습니다. 이후 기능을 확장할 때도 회원 기록과 트레이너 피드백을 연결한다는 목적은 유지했습니다. [v1.0](reference/식단관리앱_개발기획안_v1_0.md) · [v1.1](reference/식단관리앱_개발기획안_v1_1.md) · [v1.2](reference/식단관리앱_개발기획안_v1_2.md)

## 실제 사용으로 이어진 범위

기획안 v1.2를 기준으로 화면 시안을 만들고 앱 v1.0을 배포했습니다. 시안은 [단일 HTML 파일](reference/식단관리앱_와이어프레임_v1_0.html)로 남아 있습니다. 앱의 처리 규칙도 이 시안에서 출발했습니다([`status.ts`](../src/lib/status.ts)).

담당 트레이너와 제가 먼저 써 본 뒤, 센터의 다른 회원들도 사용하기 시작했습니다. 가입과 사용 현황은 [README](../README.md#실제-사용-현황)에 정리했습니다.

전체 기능과 화면 구성은 [현재 제품 기획](reference/FITORY_제품기획.md)에 있습니다. 식단·운동·인바디를 함께 보는 흐름은 [운동 기록과 변화 보고서](07_운동기록과_코칭보고서.md)에 정리했습니다.
