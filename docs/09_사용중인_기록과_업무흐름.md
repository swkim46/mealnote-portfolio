# 기록을 지키면서 사용자의 조작을 줄입니다

[FITORY](../README.md)

회원이 운동 중에 짧게 남기는 기록과 트레이너가 여러 회원을 확인하며 남기는 설명은 저장을 기다리는 방식도 달라야 합니다. 저는 입력을 지키는 처리와 화면을 사용하는 흐름을 함께 보며 개선했습니다.

## 메모를 저장하는 동안에도 다른 기록으로 이동합니다

운동 메모를 저장할 때마다 사용자를 화면에 붙잡아 두면 다음 기록을 확인하기 어렵습니다. 저는 저장 중에도 이동할 수 있도록 요구했습니다. 구현에서는 요청을 보낼 때의 운동·입력 내용을 보존하고, 화면이 바뀌어도 그 요청의 결과를 처리하도록 구성했습니다.

통신이 실패했을 때는 쓰던 내용을 잃지 않아야 합니다. 처음 제안된 방식은 ‘저장하지 못한 메모’ 카드를 만들고 사용자가 ‘이어서 작성하기’나 ‘버리기’를 고르는 것이었습니다. 저는 복원 조작이 과하다고 판단했습니다.

현재는 해당 메모 입력란을 다시 볼 때 다른 글을 작성 중이지 않으면 실패한 글을 바로 이어 쓸 수 있게 합니다. 다른 기기에서 서버의 메모가 달라진 경우에는 충돌을 안내합니다. 늦게 도착한 이전 저장 결과가 더 새로 쓴 글을 가리지 않도록 요청 순서와 표시 상태도 함께 관리합니다.

여기서 제가 정한 것은 이동을 허용하는 사용 흐름과 복원 조작의 단순화입니다. 요청 순서와 충돌 처리의 세부 구현은 Claude Code와 Codex의 구현·검토를 거쳐 보강했습니다.

## 필수 입력과 참고 정보를 구분합니다

식단 등록에서는 필수 항목을 먼저 두고 사진과 한마디를 이어 배치했습니다. 사진을 고른 뒤에도 입력 화면이 지나치게 길어지지 않도록 미리보기 크기와 간격을 조정했습니다.

운동 기록에서는 이전 기록을 참고할 수 있게 하되 화면을 과하게 늘리지 않도록 대표 세트 정보를 보여줍니다. 운동별로 더 자세한 기록이 필요하면 검색에서 찾아봅니다. 한 화면에서 바로 할 일과 필요할 때 열어볼 정보를 나눈 것입니다.

## 회원과 트레이너에게 필요한 알림을 다르게 정합니다

회원은 자신의 기록에 대한 피드백을 기다리고, 트레이너는 여러 회원의 기록을 확인합니다. 회원에게는 피드백을 바로 알리고 트레이너에게는 처리할 일을 모아 알리도록 했습니다.

확인한 식사와 답변한 메시지는 목록과 알림에서 같은 상태로 다룹니다. ‘답변 없이 확인’한 메시지를 다시 답변 대기로 알리지 않도록 처리 기준을 연결했습니다. [확인·답변 규칙](02_트레이너_업무_흐름과_처리_규칙.md) · [알림 설계](04_알림_설계.md)

## 실제 사용하는 조건으로 검토합니다

초기에는 같은 와이파이의 휴대폰에서 식단 저장이 실패했지만, 개발 PC의 접속 방식으로는 문제가 드러나지 않았습니다. 이후 휴대폰 접속 조건도 검증에 포함했습니다. 새 기능에서도 회원 이동, 저장 중 화면 이탈, 다른 기기 수정처럼 사용 중 생길 수 있는 조건을 확인합니다.

검토에서 재현한 문제는 수정 후 같은 조건에서 다시 확인합니다. 기술적으로 동작하는 것과 의도한 사용 흐름이 맞는지도 함께 봅니다. 기능이 정상이어도 복원 조작이 과하면 다시 설계한 메모 사례가 그 기준을 보여줍니다.
