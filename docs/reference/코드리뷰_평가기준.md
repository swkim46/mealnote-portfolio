# 식단노트 코드 리뷰 평가 기준

2026-10-27 사용자 요청에 따라 적용한다. 새 기능이 동작하는지와 함께, 기존 앱에 일관되게 통합됐는지와 다음 변경을 감당할 수 있는지를 평가한다. 새 코드와 직접 연결되는 기존 코드를 함께 읽는다.

## 평가 항목

| 항목 | 확인할 내용 | 문제가 있다고 판단할 근거 |
|---|---|---|
| 기존 구조와의 연계 | 기존 데이터 저장소, 조회 범위, 화면 이동, 인증, 업데이트·입력 보존 방식을 이해하고 연결했는가 | 새 진입 경로에서만 데이터가 사라짐, 과거에 해결한 경쟁 상황이 다시 생김, 같은 동작을 서로 다른 규칙으로 처리함 |
| 도메인 규칙과 기준 데이터 | 읽음, 확인 완료, 새 피드백, 기기별·계정별 설정의 의미가 명확한가. UI·SQL·서비스워커가 같은 의미를 쓰는가 | 같은 알림의 정체성을 현재 식사 상태로 대체함, 두 화면의 판정이 다름, 한 규칙을 고칠 때 여러 곳을 찾아야 하지만 대응 관계가 없음 |
| 책임과 의존성 | 화면 표시, 서버 통신, 브라우저 기능, 업무 규칙의 경계가 이해되는가. 새 기능 때문에 핵심 경로의 의존성이 불필요하게 커졌는가 | 설정 API 수정이 화면 이동·로그아웃 코드까지 건드리게 됨, 한 함수가 여러 작업의 순서와 복구 정책을 모두 떠맡음 |
| 상태와 비동기 처리 | 중복 조회, 늦은 응답, 연속 저장, 계정·화면 전환, 타이머·구독 정리가 안전한가 | 오래된 응답이 새 상태를 덮음, 화면과 서버가 달라짐, 이전 저장 실패가 다음 변경까지 되돌림 |
| 오류와 복구 | 조회 실패·데이터 없음·꺼짐·처리 중·성공을 구분하는가. 재시도와 부분 성공의 의미가 명확한가 | 실패를 기본값이나 빈 목록으로 바꿈, 실제로 읽지 못했는데 읽음 처리함, 저장 여부가 불명확한데 성공 안내함 |
| 데이터 접근과 비용 | 조회 범위, 페이지 처리, 정렬, 인덱스, 반복 요청, 보관·정리 범위가 사용자 규모에 맞는가 | 고정 상한 이후 접근 불가, 전체 조회를 타이머로 반복, 오래된 상세를 잠깐 불러왔다가 재조회에서 잃음 |
| 보안과 데이터 무결성 | 권한·세션 검사를 서버에서 보장하는가. 여러 기기·중복 요청에서도 데이터가 보존되는가 | UI만 막음, 만료 세션이 접근함, 다른 기기의 변경이나 저장된 사진을 덮어쓰거나 지움 |
| 타입·계약·가독성 | 상태 이름과 반환값이 실제 의미를 나타내는가. 외부 데이터 경계를 검증하는가. 상수·정책의 중복이 관리되는가 | 타입 단언으로 서버 응답을 그대로 믿음, 같은 이름이 서로 다른 성공 단계를 뜻함, 숫자·문자열의 의미나 변경 위치를 찾기 어려움 |
| 테스트의 실효성 | 사용자 흐름과 실패·경쟁 상황을 검증하는가. 새 코드가 기존 기능과 만나는 경계를 다루는가 | 정상 순서만 통과함, 이전 코드에서도 새 검증이 통과함, 실제 워커 대신 준비된 저장값만 시험하고 전체 경로를 검증했다고 표현함 |
| 변경 범위와 운영 가능성 | 필요한 최소 범위인가. 마이그레이션 적용 순서·기존 데이터 호환·문제 추적·문서가 맞는가 | 기능 하나 때문에 불필요하게 구조를 바꿈, 반대로 필요한 공통 정책을 새 화면에 복사함, 실패 원인을 구분할 단서가 없음 |

## 리뷰 방법

1. 변경 목적과 기준 커밋, 미커밋 파일, 관련 기존 동작을 먼저 확인한다. `git diff`만 읽고 끝내지 않는다.
2. 기존 구현에서 재사용할 수 있는 규칙과 보호 장치를 찾는다. 그대로 재사용하기 어려우면 새 경계가 필요한 이유를 평가한다. 기존 코드가 있다는 이유만으로 좋은 설계라고 가정하지 않는다.
3. 기능별 정상 흐름과 함께, 기존 기능과 연결되는 흐름을 확인한다. 예를 들어 알림에서 오래된 식사 열기 → 재조회 → 댓글 작성, 설정 조회 실패 → 복구 → 변경, 다른 기기 변경 → 현재 화면 갱신을 본다.
4. 비동기는 요청 시작 순서와 완료 순서를 따로 검토한다. 조회뿐 아니라 저장 두 개, 실패와 성공, 재시도와 새 작업의 교차도 포함한다.
5. 구체적인 영향이 있는 의심은 작은 재현으로 확인한다. 재현 스크립트는 `app/scripts/review-local/`에 두고 기존 git ignore를 유지한다. 운영 데이터나 실제 알림 전송이 필요한 검증은 별도 범위로 표시한다.
6. 재현되는 결함과 구조·유지보수 의견을 나눠 보고한다. 두 종류 모두 작성하되, 이번 변경에서 문제가 확인되지 않은 기존 코드의 대규모 정리는 요구하지 않는다.

## 의견에 필요한 근거

각 의견에는 해당 위치, 현재 동작 또는 구조, 기존 코드와의 관계, 사용자 영향 또는 구체적인 변경 비용, 작은 수정 방향을 적는다. 결함에는 재현 조건과 검증 결과도 붙인다. 추정은 확인된 사실처럼 쓰지 않는다.

- **결함:** P0~P3으로 영향과 긴급도를 표시한다. 보안·데이터 손실·일상 동작의 오류를 우선한다.
- **이번 변경에서 정리할 품질 문제:** 새 기능이 기존 보호 장치를 빠뜨렸거나 같은 정책을 충돌하게 만든 경우. 결함을 고치면서 원인도 함께 정리한다.
- **후속 개선:** 현재 동작은 가능하지만 책임·계약이 불명확해 다음 변경 비용이 커지는 경우. 어떤 변경이 어려워지는지 설명한다.
- **취향:** 파일 길이, 이름 선호, 폴더 배치만으로 결함이나 필수 수정이라고 판정하지 않는다.

공통화는 같은 규칙을 함께 바꿔야 할 때 제안한다. 비슷한 코드 몇 줄이 있다는 이유만으로 추상화하지 않는다. 반대로 이미 효과가 확인된 요청 순서 보호·오류 구분을 새 기능에서 빠뜨린 것은 단순 취향으로 넘기지 않는다. 별도 프레임워크나 대규모 재설계 없이 고칠 수 있는지 먼저 본다.

## 결과물 형식

매 리뷰는 다음을 구분해 남긴다.

1. 결함과 재현 결과
2. 코드 품질 평가: 기존 구조를 잘 따른 부분, 누락·불일치, 이번에 정리할 부분과 후속 개선
3. 검증 범위와 남은 불확실성

테스트 개수나 임의의 총점으로 품질을 대신하지 않는다. 결함이 없더라도 구조 문제가 있으면 설명하고, 구조가 깔끔해도 동작 결함이 있으면 별도로 보고한다. 재리뷰에서는 이전 지적의 해결 여부와 새로 확인한 사항을 구분한다.
