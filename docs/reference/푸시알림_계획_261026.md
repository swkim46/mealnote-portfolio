작성 2026-10-26 · 대상 앱 코드(dev 브랜치) · 지금 운영 v1.6.1
2차 수정: 사용자 결정 다섯 가지와 Codex 피드백(`푸시알림_계획_피드백_261026.md`)을 반영했다. 남은 결정(요약 주기·기록 알림 시각·설정 범위·시험 환경)도 같은 날 정해 반영했다. 3차 수정: Codex 2차 피드백(`푸시알림_계획_2차피드백_261026.md`)을 구현 메모에 반영했다. 4차: 시험 전 DB 검사를 최종 적용 값 기준으로 바꿨다(Codex 3차). 5차(구현 중, 2026-10-27): 피드백 알림은 묶지 않고 바로 보내고, 알림 목록 화면을 더했다(아래 '구현 중 바뀐 것').

## 무엇을 하나

앱을 닫아 두어도 휴대폰 알림으로 새 소식을 받게 한다. 알림은 일이 생길 때마다 하나씩 보내지 않는다. **정해진 시각에 아직 확인하지 않은 새 소식이 있는지 보고, 있으면 한 번 보낸다.**

- 트레이너는 6시간마다(설정에서 3시간으로 바꿀 수 있음) '확인할 식사 기록과 답할 질문이 있다'는 요약을 받는다. 회원마다 따로 오지 않는다.
- 회원은 트레이너가 피드백을 남기면 바로 알림을 받는다. 묶지 않으므로 피드백마다 알림이 따로 쌓인다(2026-10-27 사용자 결정).
- 회원은 낮 1시에 점심 기록이 없으면, 저녁 8시에 저녁 기록이 없으면 기록하라는 알림을 받는다. 점심을 기록해도 저녁을 잊을 수 있어서 두 번 확인한다.

앱 안의 점과 확인 목록은 지금처럼 그대로 있다. 알림이 늦거나 오지 않아도 앱을 열면 모든 소식을 볼 수 있다.

알림은 **각자 내 정보에서 '알림 받기'를 켠 기기에만** 간다.

## 보내는 알림

| 알림 | 받는 사람 | 언제 | 문구 예 | 누르면 |
|---|---|---|---|---|
| 확인할 소식 요약 | 트레이너 | 6시간마다(9·15·21시), 설정에서 3시간마다(9·12·15·18·21시)로 바꿀 수 있음. 지난 요약 뒤에 새로 들어와 아직 확인하지 않은 것이 있을 때만 | 확인할 식사 기록 3건, 답할 질문 1건이 있어요 | 확인 목록 |
| 새 피드백 | 회원 | 트레이너가 평가나 답글을 저장하면 바로(앱이 저장 직후 서버 기능을 부름). 보내기 전에 회원이 읽었으면 보내지 않음 | 트레이너가 피드백을 남겼어요 | 피드백 탭 |
| 점심 기록 | 회원 | 낮 1시, 오늘 점심 기록이 없을 때만 | 점심 식단을 남겨 주세요 | 오늘 탭의 식단 기록 |
| 저녁 기록 | 회원 | 저녁 8시, 오늘 저녁 기록이 없을 때만 | 저녁 식단을 남겨 주세요 | 오늘 탭의 식단 기록 |

- **질문**에는 댓글뿐 아니라 회원이 식사의 한마디를 새로 쓰거나 고친 것도 들어간다. 앱이 이미 이것을 '답을 기다리는 질문'으로 다루기 때문이다.
- **잠금 화면에는 이름도 내용도 쓰지 않는다.** 위 문구처럼 건수와 종류만 쓴다. 식단 내용, 남긴 글, 평가 결과, 인바디 수치, 회원 닉네임은 앱을 열어야 보인다.
- 밤 시간 제한은 두지 않는다. 필요하면 각자 휴대폰의 방해 금지 모드로 조절한다(사용자 결정).
- 알림을 눌렀다고 읽음으로 치지 않는다. 앱 화면에서 실제로 확인했을 때만 지금처럼 읽음·확인 처리된다.

## 설정

- **기기마다**: 내 정보의 '알림 받기'를 켜고 끄는 것은 그 기기에만 적용된다.
- **종류별**: '확인할 소식 요약'(트레이너), '새 피드백'·'기록 알림'(회원)을 각각 켜고 끌 수 있다. 계정 전체에 적용된다 — 한 기기에서 끄면 다른 기기도 꺼지고, 화면에 '모든 기기에 적용'이라고 쓴다(사용자 결정).
- **요약 주기**: 트레이너는 '하루 3회(9·15·21시)'(기본, 6시간 간격)와 '하루 5회(9·12·15·18·21시)'(3시간 간격) 중에서 고른다. 화면에는 실제 시각대로 쓴다. 이것도 계정 전체에 적용된다.
- 아이폰은 사람이 버튼을 눌렀을 때만 알림 허용 창을 띄울 수 있다. 그래서 앱이 처음 열릴 때 묻지 않고 '알림 받기'를 누를 때 묻는다.
- '허용 안 함'을 누른 기기는 앱이 다시 물을 수 없으므로, 휴대폰 설정에서 켜는 방법을 안내한다.
- 켜는 과정은 '허용 → 이 기기 등록 → 서버 저장 → 시험 알림 접수'로 나뉜다. 서버 저장이 실패하면 '알림을 켰어요'라고 하지 않고 실패를 알린다.
- 알림 서버가 받았다고 휴대폰에 도착했다는 뜻은 아니다. 집중 모드·네트워크·휴대폰 설정에 따라 늦거나 안 보일 수 있으므로, 안내 문구에 '놓치지 않는다'는 표현을 쓰지 않는다.

## 기기별로 되는 것

| 기기 | 받을 수 있나 | 조건 |
|---|---|---|
| 아이폰·아이패드 | 받을 수 있음 | iOS·iPadOS 16.4 이상에서 홈 화면에 추가한 앱으로 열었을 때. 브라우저 탭으로 연 화면에서는 켤 수 없다 |
| 안드로이드 | 받을 수 있음 | 크롬 브라우저와 설치한 앱 모두 |
| PC | 받을 수 있음 | 크롬·엣지·파이어폭스·맥 Safari 등 |

- 받을 수 있는지는 브라우저 이름이 아니라 기능 지원과 설치 상태로 판단한다. 받을 수 없는 아이폰 화면에는 '홈 화면에 추가하면 알림을 받을 수 있어요'라는 안내를 기존 설치 안내와 이어 보여 준다.

## 로그아웃·PIN·계정 되찾기와 알림

| 일 | 다른 기기의 알림 |
|---|---|
| 로그아웃 | 지금 로그아웃은 같은 계정의 모든 기기를 로그아웃시키므로, 모든 기기의 알림이 멈춘다 |
| 계정 되찾기('내가 아니에요') | 다른 기기가 로그아웃되므로 그 기기들의 알림도 멈춘다 |
| 일반 PIN 변경 | 다른 기기는 로그인 상태로 남으므로 알림도 계속 간다(지금 동작 유지) |

- 푸시 작업에서 로그인·PIN 정책은 바꾸지 않는다. PIN을 바꿀 때 다른 기기 알림도 끄고 싶으면 따로 정한다.
- 이미 알림 서버에 넘긴 알림은 거둘 수 없다. 로그아웃 직전에 넘긴 알림 하나는 도착할 수 있다.

## 시험 순서

실제 휴대폰 확인은 **운영 배포 전에** 한다. 알림을 켜지 않은 사용자도 바뀐 서비스워커(앱을 설치형으로 돌리는 배경 코드)는 함께 받기 때문이다. 운영 DB의 식사 저장 쪽은 이번 설계에서 바꾸지 않는다.

| 순서 | 내용 | 끝나는 기준 |
|---|---|---|
| 1 | 최소 검증: 임시 터널 https 주소의 설치 앱에서 허용 → 등록 → 실제 알림 1건 수신 → 누르면 앱으로(열려 있을 때·닫혀 있을 때) | 운영자 아이폰과 안드로이드 또는 PC 한 대에서 수신·이동 확인 |
| 2 | 기기 등록: 다시 로그인, 같은 기기에서 다른 계정으로 로그인, 끄기, 세션 종료, 저장 실패 | 로컬 검증 통과 |
| 3 | 알림 종류별 내용과 이동: 요약·새 피드백·점심·저녁 기록, 작성 중인 입력을 지우지 않는 이동 | 로컬 검증 통과 |
| 4 | 임시 터널 주소에서 두 휴대폰(회원·트레이너)으로 모든 종류 확인 → 전체 검증 → Codex 리뷰 | 실제 수신·이동, 전체 검증 통과, 리뷰 조치 |
| 5 | 운영 배포. 송신 스위치를 '시험 계정만'으로 두고 배포한다 | 허용한 두 계정(운영자·트레이너)의 휴대폰에서 수신 확인 뒤 '전체'로 켬 |

## 실제 휴대폰 시험 환경

새 Supabase 프로젝트는 만들지 않는다. **지금 쓰는 로컬 시험 환경을 그대로 쓰고, 휴대폰에서 열 수 있는 https 주소만 잠시 붙인다**(사용자 질문 반영).

- 로컬 검증만으로 끝내지 못하는 이유: 휴대폰 알림은 https 주소로 연 앱에서만 켤 수 있다. 지금 맥에서 띄우는 시험 앱은 http 주소라, 아이폰이 알림 허용 자체를 막는다.
- 방법: Cloudflare의 임시 터널(`cloudflared`)로 맥의 시험 앱에 https 주소를 붙인다. 휴대폰 시험 전용 빌드를 따로 만들어, 앱이 DB 요청을 같은 https 주소 안의 `/supabase` 경로로 보내고 맥이 그 요청을 로컬 DB로 넘기게 한다. 운영 DB와 운영 사용자는 건드리지 않는다.
- 시험을 시작하는 명령이 먼저 DB 주소가 로컬인지 확인한다. 운영 주소가 섞여 있으면 빌드·터널을 띄우지 않고 멈춘다.
- 알림을 보내는 서버 기능도 맥에서 돌고, 애플·구글 알림 서버로는 맥이 직접 보낸다.
- 주의: 터널을 켤 때마다 주소가 바뀌므로, 시험할 때마다 휴대폰에서 홈 화면에 다시 추가한다. 터널이 켜져 있는 동안은 그 주소를 아는 사람이 시험 앱에 들어올 수 있으므로, 시험 데이터만 두고 시험이 끝나면 바로 끈다.
- 맥에 `cloudflared`를 설치해야 한다(Homebrew). 설치 전에 확인을 받는다.

## 구현 중 바뀐 것(2026-10-27)

- **새 피드백은 바로**(사용자 결정): 3분 기다려 묶던 규칙을 없앴다. 트레이너가 평가·답글을 저장하면 앱이 `push_nudge`로 서버 기능을 바로 부른다. 저장과 따로 부르므로 실패해도 저장에는 영향이 없고, 트레이너 계정당 10초에 한 번만 받는다. 알림마다 tag가 달라 휴대폰에 따로 쌓인다.
- **피드백을 식사 단위로 기록**: '마지막으로 알림을 만든 시각' 하나로 자르면, 저장과 알림 만들기가 겹칠 때 기준보다 앞 시각으로 들어온 피드백을 영영 놓친다. 식사마다 어느 피드백까지 알렸는지(`private.push_feedback_sent`)를 두고, 알림에는 알리는 식사들(`meal_ids`)을 적어 다시 보낼 때 그 식사들이 아직 안 읽혔는지로 확인한다. 트레이너 요약은 기준 시각을 30초 겹쳐 본다.
- **알림 목록**(사용자 요청): 머리글 종 버튼. 최근 1주일 동안의 소식을 시간순으로 보여 주고 누르면 그 식사 상세로 간다. 회원은 트레이너 평가·답글, 트레이너는 담당 회원의 기록·말(댓글·고친 한마디). 끼니 기록 알림은 목록에 넣지 않는다. 앱 안 화면이라 이름을 보여 준다. 목록을 연 시각은 서버 시계로 남긴다(`activity_seen`, `mark_activity_seen`). 마이그레이션 `20261027000001_activity.sql`.
- 내 정보의 줄과 창 이름을 '알림 설정'으로 바꿨다(종 버튼 '알림 목록'과 구분).
- 작성 중에 알림을 누르면 '새 소식 보기' 띠 대신, 작성 창을 그대로 두고 뒤 화면만 바꾼다(쓰던 내용 유지).
- 실제 휴대폰 확인(2026-10-27, 임시 터널 + 로컬 DB): 시험 알림·새 피드백·점심 기록·트레이너 요약 수신, 누르면 해당 화면 이동, 같은 휴대폰 계정 전환 뒤 이전 계정 알림 없음.

## 구현 메모

**보내는 방식: 상태를 훑어 알림을 만들고, 보낼 때마다 다시 확인**
- 식사·댓글 저장 경로에 새 트리거를 달지 않는다. 10분마다 지금 상태를 조회해 보낼 알림을 만든다.
- 알림을 만든 뒤에도 전송 대기·재시도 사이에 상태가 바뀔 수 있다. 그래서 **처음 보낼 때와 모든 재시도 직전에** 그 알림의 근거가 아직 유효한지 다시 확인하고, 근거가 없어졌으면 전송을 취소한다(Codex 2차 2).
- 알림 문구에는 건수와 종류만 쓴다. 판정에는 작성자 구분·한마디 유무·시각·ID 같은 상태 정보를 읽지만, 식단·댓글 원문은 문구 생성에 쓰지 않는다.

**판정 함수 — 앱의 `status.ts`와 같은 의미로**(Codex 2차 1)
- 질문 대기와 확인 필요는 `member_msg_at > trainer_msg_at` 비교로 내지 않는다. `trainer_msg_at`은 평가 시각으로도 바뀌고, '답변 없이 확인'(`reviewed_at`)을 반영하지 못하며, 첫 질문처럼 NULL인 경우를 놓치기 때문이다.
- `private.meal_pending_question(meal)`: `thread()`와 같은 규칙으로 마지막 대화를 정한다.
  - 회원 쪽 마지막 시각 = 한마디가 비어 있지 않으면 `coalesce(note_updated_at, created_at)`, 회원 댓글의 최댓값 중 큰 값.
  - 트레이너 쪽 마지막 시각 = 트레이너 댓글의 최댓값(평가 시각은 대화가 아니므로 넣지 않음).
  - 마지막이 회원 쪽이고, `reviewed_at`이 NULL이거나 그 회원 시각보다 이르면 질문 대기.
- `private.meal_needs_trainer(meal)` = `reviewed_at is null or meal_pending_question(meal)`(`needsTrainer`와 같음).
- `private.meal_new_feedback(meal)` = 마지막 트레이너 댓글 시각이나 `rated_at`이 `member_seen_at`보다 늦음(`hasNewFeedback`와 같음).
- 대조 검증: 첫 회원 질문 · 답변 없이 확인 · 확인 뒤 새 질문 · 한마디 수정 · 트레이너 답변 뒤 · 평가만 남김을 만들어, SQL 판정과 화면(확인 목록·답변 대기·피드백 NEW) 판정이 같은지 본다.

**알림별 근거와 다시 확인할 것**

| 알림 | 만들 때 | 보낼 때마다 다시 확인 | 근거 범위(알림에 저장) |
|---|---|---|---|
| 확인할 소식 요약 | 트레이너의 요약 시각이 지났고, 지난 요약 기준 시각 뒤에 들어와 `meal_needs_trainer`인 담당 회원 식사가 있음 | 담당 회원의 `meal_needs_trainer` 건수를 지금 다시 센다. 0이면 취소, 아니면 지금 건수로 문구를 만든다 | 회차 키(날짜·시) |
| 새 피드백 | `meal_new_feedback`인 식사 중 피드백 시각이 지난 피드백 알림 기준 시각 뒤인 것이 있음 | 이 알림의 범위(`basis_from`～`basis_until`) 안의 피드백이 아직 안 읽힌 채 남아 있는지. 범위 밖의 새 피드백은 다음 알림이 맡는다 | `basis_from`·`basis_until` |
| 점심·저녁 기록 | 13·20시가 지났고 그날 그 끼니 기록이 없음 | 여전히 그 끼니 기록이 없는지, 날짜가 바뀌지 않았는지 | 날짜·끼니 |

- 모든 알림 공통으로 보낼 때마다: `알림.user_id = 구독.user_id = 세션의 user_id`이고 그 세션이 `auth.sessions`에 남아 있는지(세션이 하나 있다는 것만으로 통과하지 않음, Codex 2차 3) · 종류 설정이 켜져 있는지 · 송신 스위치가 허용하는지 · 담당 관계가 그대로인지 · `expires_at` 전인지.

**표**(마이그레이션 하나, 새 표마다 `session_alive` restrictive 정책)
- `public.push_subscriptions(id, user_id, session_id, endpoint unique, p256dh, auth, created_at, last_accepted_at)`. 행은 RPC로만 만든다.
  - `register_push(endpoint, p256dh, auth)`: `user_id`·`session_id`는 서버가 `auth.uid()`와 JWT의 `session_id`에서 정한다.
  - **같은 endpoint가 다른 사용자로 등록되면 기존 행을 지우고(전송 대기도 함께 지워짐) 새 ID로 만든다.** 이전 계정의 재시도가 새 계정에게 가지 않는다(Codex 2차 3). 같은 사용자의 다시 등록은 키·세션만 고친다.
  - endpoint는 알려진 푸시 서비스 주소(FCM·애플·모질라·윈도우)만 받는다. endpoint와 키는 로그에 남기지 않는다.
  - `unregister_push(endpoint)`: 본인 것만. 로그아웃 직전에 부른다.
- `public.push_prefs(user_id, digest, digest_times '3'|'5', feedback, reminder)`: 계정 전체 설정. 기본은 모두 켬·하루 3회.
- `private.push_state(user_id, digest_basis_at, feedback_basis_at, lunch_on, dinner_on)`: **알림을 만든 기준**이다(외부 서버 접수 기준이 아님). 켠 기기가 없거나 그 종류를 꺼서 알림을 만들지 않았으면 기준을 옮기지 않는다.
- `private.push_notifications(id, user_id, kind, slot_key, basis_from, basis_until, created_at, expires_at)`, `unique (user_id, kind, slot_key)`.
  - `slot_key`: 요약은 `2026-10-27 15`, 기록은 `2026-10-27 점심`, 피드백은 `basis_until`.
- `private.push_deliveries(notification_id, subscription_id, status, attempts, next_try_at, locked_until, last_error_code)`, `unique (notification_id, subscription_id)`. 한 기기만 실패하면 그 기기만 다시 보낸다.
- `public.app_settings`의 송신 스위치: `push_mode = 'off'|'testers'|'all'`과 시험 허용 사용자 목록.

**만들기와 선점의 중복 방지**(Codex 2차 4)
- 만들기: 사용자별 `push_state` 행을 `for update`로 먼저 잠근 뒤 대상 판정 → 알림 생성 → 기준 시각 갱신을 한 트랜잭션에서 한다. 여기에 `(user_id, kind, slot_key)` 고유 제약을 더해, 두 호출이 겹쳐도 알림은 하나만 생긴다.
- 선점: 보낼 전송 행을 `for update skip locked`로 가져가며 `locked_until`을 건다. 같은 전송을 두 호출이 동시에 가져가지 않는다. 처리 중 함수가 죽으면 `locked_until`이 지난 뒤 다시 가져간다.
- 응답 처리: 201은 접수(`last_accepted_at`, 도착이 아님) · 404·410은 구독 삭제 · 429는 `Retry-After`만큼 미룸 · 5xx·네트워크 오류는 늘어나는 간격으로 최대 3번 · 400·403(키·인증 문제)은 재시도하지 않고 기록.
- 푸시 메시지의 TTL은 종류에 맞춰 짧게 둔다(요약은 다음 회차 전까지). `tag`를 종류별로 같게 두어 같은 종류의 새 알림이 이전 알림을 덮게 한다. 중복을 완전히 막는다고 약속하지 않고, 생겨도 하나만 남게 하는 방법이다.
- 검증: 두 호출을 같은 시점의 대상 판정에서 겹치게 실행해 **알림 생성 수**가 1인지 본다(같은 전송 행을 두 번 가져가지 않는지만 보지 않는다).

**보내는 서버 기능** — Supabase Edge Function `send-push`(Deno).
- `pg_cron`이 10분마다 `pg_net`으로 부른다. 회차(요약 3회·5회, 기록 13·20시)가 지났는지는 `push_claim` 안에서 판단한다.
- 인증: 함수는 `verify_jwt = false`로 두고, 공유 비밀 머리글을 함수 첫 줄에서 검사한다. 비밀은 Vault(DB 쪽)와 함수 비밀에만 둔다.
- DB 접근: `private` 스키마는 API에 노출되지 않는다. 함수는 서비스 키로 `public`의 `push_claim`·`push_report` RPC만 부르고, 두 RPC는 `service_role`에만 실행 권한을 준다. 서비스 권한은 RLS를 건너뛰므로 위의 '보낼 때마다 다시 확인'을 RPC 안에서 한다.
- 웹 푸시 암호화와 VAPID 서명은 검증된 라이브러리를 쓴다. 시험 순서 1에서 Deno 동작과 아이폰 수신을 먼저 확인한 뒤 확정한다.

**서비스워커와 알림 누르기**
- 지금 방식(generateSW)을 유지하고 `workbox.importScripts`로 `public/push-sw.js`를 붙인다. 새 버전 적용 흐름(`appUpdate.ts`, `clientsClaim: false`)은 건드리지 않고, 새 버전 적용 검증 17건과 '푸시 없는 옛 버전 → 새 버전' 전환을 함께 확인한다.
- 알림 데이터에는 알림 ID·받는 계정 ID·이동할 화면 종류(`queue`·`feedback`·`today`)만 넣는다. 주소에는 계정 ID를 넣지 않는다.
- `notificationclick`
  - 열린 앱 창이 있으면 창을 앞으로 가져오고 `postMessage`로 위 세 값을 전달한다. 주소를 바꿔 새로 고치지 않으므로 작성 중인 식단·댓글이 남는다. 입력 중(`isBusy`)이면 바로 넘기지 않고 '새 소식 보기' 띠를 띄운다.
  - 열린 창이 없으면 위 세 값을 서비스워커의 IndexedDB에 잠시 적고 `/`를 연다. 앱은 로그인·프로필 확인이 끝난 뒤 그 값을 읽고 지운다. 로그인 전이면 로그인 뒤에 읽는다.
  - 두 경우 모두 받는 계정 ID와 지금 로그인 계정이 다르면 이동하지 않고 지금 계정의 기본 화면을 보인다. 화면 종류는 세 값 말고는 무시한다.

**앱**
- `src/lib/push.ts`: 지원 여부, 켜기(버튼 클릭 안에서 권한 → 구독 → `register_push` → 시험 알림), 끄기, 로그아웃 직전 `unregister_push`.
- 앱이 다시 앞으로 올 때 권한·브라우저 구독·서버 등록을 맞춘다(권한이 꺼졌으면 서버 등록 삭제, 구독이 바뀌었으면 다시 등록).
- 공개 VAPID 키는 `VITE_VAPID_PUBLIC_KEY`. 환경(로컬·휴대폰 시험·운영)마다 키·비밀·구독이 따로다.

**휴대폰 시험 빌드**(Codex 2차 5)
- 지금 `supabase.ts`는 `import.meta.env.DEV`일 때만 로컬 주소를 같은 출처의 `/supabase`로 바꾼다. 빌드본은 `DEV=false`이므로 이 조건을 타지 않고, 그대로 두면 휴대폰이 자기 자신의 `127.0.0.1`로 접속한다.
- `phonetest` 모드를 새로 둔다: `.env.phonetest`에 로컬 Supabase 주소·공개 키와 `VITE_SUPABASE_SAME_ORIGIN=1`을 둔다. `supabase.ts`는 `(DEV || VITE_SUPABASE_SAME_ORIGIN === '1') && isLocal`일 때 `${location.origin}/supabase`를 쓴다. 운영 빌드에는 이 값이 없으므로 운영 동작은 바뀌지 않는다.
- `vite.config.ts`: `preview.proxy`에 개발 서버와 같은 `/supabase` 전달, `phonetest` 모드일 때만 `preview.allowedHosts = ['.trycloudflare.com']`. `__CHANNEL__`은 production이 아니므로 dev(테스트 환경 띠 표시)다.
- `npm run phone:test`(`scripts/phone-test.sh`):
  1. **Vite가 최종 적용할 DB 주소**가 `127.0.0.1`·`localhost`인지 확인한다. 파일 원문이 아니라 `loadEnv('phonetest')`에 셸 환경 변수를 덮어쓴 값(`.env.phonetest.local`·셸 변수 포함, Vite 우선순위 그대로)을 본다. 빌드 설정(`vite.config.ts`)에서도 같은 검사를 해, 스크립트를 거치지 않고 `vite build --mode phonetest`를 직접 불러도 멈춘다. 키 원문은 출력하지 않는다.
     - 검증: 셸 환경 변수 `VITE_SUPABASE_URL`에 운영 DB 주소를 넣고 실행하면 빌드와 터널이 시작되지 않고 멈춘다(Codex 3차).
  2. `vite build --mode phonetest` → `vite preview --mode phonetest`.
  3. `cloudflared tunnel --url http://localhost:<포트>`로 주소를 받아 출력한다. 끝나면 둘 다 끈다.
- 로컬 Edge Function과 `pg_cron`·`pg_net`은 Docker 안에서 돈다. 함수가 실제 애플·구글 알림 서버로 보내려면 시험용 VAPID 키를 로컬 함수 비밀로 둔다.
- 검증: 휴대폰에서 식단 조회·저장이 터널을 거쳐 로컬 DB로만 가는지(운영 DB 기록이 없는지) 보고, 서비스워커가 켜진 상태에서 실제 알림 수신까지 이어지는지 본다.

**검증 추가**
- 권한: 구독·설정 RLS, 남의 구독 못 지움, `push_claim`·`push_report`는 회원·트레이너가 못 부름, 등록 시 서버가 세션을 정함, 알려진 푸시 주소만 등록.
- 판정 대조: 위 '판정 함수'의 여섯 상황에서 SQL과 화면 판정이 같음.
- 상태 훑기: 요약(지난 기준 뒤 새 것·이미 확인한 것 제외·3회·5회 시각), 한마디 수정이 질문으로 잡힘, 피드백 바로·이미 읽음 제외·늦게 저장된 피드백도 놓치지 않음, 점심·저녁 기록 알림은 그 끼니 기록이 없을 때만·하루 한 번.
- 재시도 중 상태 변화: 429·일시 실패 → 피드백 읽음·확인·점심 기록 → 재시도가 취소됨. 그 뒤 새 소식은 다음 알림으로 정상 처리.
- 계정 전환: A의 전송을 429로 대기시킨 뒤 같은 endpoint를 B로 등록 → A 알림은 다시 안 감, B의 새 알림은 감.
- 동시 실행: 같은 시점의 판정에서 두 호출이 겹쳐도 알림 1건·전송 행 기기당 1건. 처리 중 종료 뒤 재개, 두 기기 중 한 대만 실패, 410 정리.
- 송신 스위치: off면 아무것도 안 감, testers면 허용 계정만, all이면 모두.
- 화면: 작성 중 알림 클릭(입력 유지), 다른 계정으로 알림 열기, 닫힌 앱에서 알림으로 열기, 로그인 전 열기.

**운영 반영**(배포 직전에 사용자 확인)
- 운영용 VAPID 키와 호출 비밀을 새로 만든다(시험용과 다른 값).
- `supabase functions deploy send-push` → `npm run db:push` → `npm run deploy`(v1.7.0, 업데이트 소식에 알림 안내).
- 송신 스위치는 `testers`(운영자·트레이너 계정만)로 두고 배포한다. 두 휴대폰에서 수신·이동을 확인한 뒤 `all`로 바꾼다.
