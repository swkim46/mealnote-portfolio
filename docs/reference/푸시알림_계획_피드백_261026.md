# 식단노트 푸시 알림 계획 피드백

검토일: 2026-10-26 · 대상: [푸시 알림 계획](./푸시알림_계획_261026.md) · 현재 코드: `51de16b`

## 검토 의견

웹 푸시를 기존 PWA에 붙이고, DB 대기열을 거쳐 서버에서 보내는 방향은 적절합니다. 다만 **실제 기기 시험 순서, PIN 변경과 세션 종료의 관계, 알림 발생 조건**은 계획을 고쳐야 합니다. **기기별 전송 상태, 야간 요약, 발송 직전 취소 조건, 알림 클릭 시 이동 방식**은 구현 전에 정해야 합니다.

아래는 아직 구현되지 않은 설계에 대한 피드백입니다. 실행 코드에서 재현한 버그 목록은 아닙니다. 계획 원문과 앱 소스는 수정하지 않았습니다.

## 유지할 방향

- 사용자가 내 정보에서 직접 알림을 켜도록 하는 흐름.
- 식단 내용·댓글 원문·평가 결과·인바디 수치를 알림에 넣지 않는 정책.
- 푸시가 오지 않아도 기존 확인 목록·피드백 화면으로 업무가 이어지는 구조.
- DB에서 발생한 일을 대기열에 기록하고 서버가 보내는 구조.
- 기존 서비스워커와 업데이트 보호 로직을 유지하려는 접근.

`generateSW`를 유지하고 `importScripts`로 푸시 처리 코드를 추가하는 방식은 가능합니다. Workbox 공식 옵션 설명도 푸시 이벤트 리스너를 추가하는 용도로 안내합니다. [Workbox importScripts](https://developer.chrome.com/docs/workbox/modules/workbox-build)

## 계획에서 고칠 내용

### 실제 휴대폰 시험을 운영 배포 앞으로 옮기기

계획 43·60·61행은 운영에 먼저 배포한 뒤 실제 iPhone에서 확인하는 순서입니다. ‘알림을 켠 사람에게만 가므로 다른 사용자에게 영향이 없다’는 설명은 범위를 좁혀야 합니다. 푸시를 꺼 둔 사용자도 변경된 서비스워커와 DB 트리거를 사용하므로, 업데이트나 식단 저장에 생기는 회귀의 영향은 받을 수 있습니다.

**권장 순서:** HTTPS 시험 주소와 시험 DB에서 실제 iPhone 홈 화면 앱·트레이너 휴대폰의 수신과 클릭을 확인한 뒤 운영에 배포합니다. 현재 LAN HTTP 주소만으로 끝내지 않습니다. 환경별 구독·대기열·VAPID 키와 호출 비밀도 분리합니다.

별도 환경을 마련하기 어렵다면 운영에서도 송신을 기본 차단하고 시험 계정만 허용하는 제한 시험 단계를 계획에 명시해 주세요. 이 경우에도 공통 서비스워커·DB 변경이 배포된다는 점은 남습니다.

iOS·iPadOS 16.4 이상 홈 화면 웹앱과 사용자 동작에 따른 권한 요청이라는 조건은 맞습니다. 다만 Safari로 설치해야만 하는 것은 아닙니다. 지원하는 다른 브라우저도 홈 화면 추가를 제공할 수 있습니다. 지원 판단은 브라우저 이름만이 아니라 기능과 설치 상태를 함께 확인합니다. [WebKit 공식 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Push 구독의 HTTPS 조건](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe)

### 일반 PIN 변경과 계정 되찾기를 구분하기

계획 50행의 ‘PIN을 바꾸면 지금처럼 다른 기기가 로그아웃된다’는 전제는 현재 코드와 다릅니다.

- 일반 PIN 변경은 [change_my_pin](../../supabase/migrations/20261021000011_lock_before_check.sql)과 [apply_pin](../../supabase/migrations/20261021000010_signup_ticket_and_locks.sql)에서 PIN과 보안 상태를 바꾸지만 다른 세션을 삭제하지 않습니다.
- 계정 되찾기는 [reclaim_account](../../supabase/migrations/20261021000010_signup_ticket_and_locks.sql)에서 다른 세션을 삭제합니다.

따라서 구독의 세션이 존재하는지만 검사하면 **일반 PIN 변경 후 다른 기기의 알림은 계속될 수 있습니다.** 현재 세션 정책을 유지할지, PIN 변경 때도 다른 기기의 알림을 끌지 따로 정해 주세요. 푸시 추가 작업에서 인증·되찾기 정책까지 암묵적으로 바꾸지는 않습니다.

로그아웃·계정 되찾기로 세션이 종료된 경우에는 발송 직전에 해당 구독의 세션이 살아 있는지 다시 검사합니다. 이미 외부 푸시 서비스에 접수된 알림까지 즉시 회수된다고 약속하지 않습니다.

### 고쳐 쓴 회원 한마디도 알림 조건에 포함하기

계획 93행은 식사 insert·평가 변경·댓글 insert만 나열합니다. 현재 앱은 식사에 처음 남긴 `note`와 고쳐 쓴 `note`도 회원 메시지로 다룹니다. [대화 구성](../../src/lib/status.ts), [메시지 시각 트리거](../../supabase/migrations/20261021000007_meal_message_times.sql)

‘이미 확인한 식사의 한마디를 질문으로 고침’도 질문 알림 대상에 포함해 주세요. 사진·음식명·시각만 바뀌거나 같은 평가를 다시 저장하는 경우는 별도로 구분합니다. 회원이 식사를 등록하며 한마디를 함께 썼을 때 기록·질문 알림을 각각 보낼지도 정해야 합니다.

## 구현 전에 구체화할 동작

### 여러 기기에 보내는 상태와 중복 처리

대기열의 `sent_at` 하나만으로 여러 구독의 성공·실패를 관리할지 불분명합니다. 예를 들어 휴대폰 A는 접수 성공, B는 시간 초과인 경우 B만 재시도할 수 있어야 합니다.

다음 구조를 기본안으로 권합니다.

- 알림 사건 또는 묶음과, **각 구독에 보내는 작업**을 구분합니다. `(알림 ID, 구독 ID)`별 상태·시도 횟수·다음 시도 시각을 관리합니다.
- 원본 사건을 식별할 키와 발생 시각, 묶음의 대상 범위를 남깁니다. 같은 사건이 두 번 쌓이지 않게 하고 읽음·처리 시각과 비교할 수 있어야 합니다.
- `pg_net`의 즉시 호출과 1분 cron이 동시에 돌아도 같은 전송 작업을 동시에 가져가지 못하게 합니다. DB의 원자적 작업 선점과 처리 중 만료 시각을 정합니다.
- 발송 중인 묶음에 새 사건을 합치지 않습니다. 발송할 범위를 확정하고 이후 사건은 다음 묶음으로 넘깁니다.
- 처리 중 함수가 종료된 작업은 정한 시간 이후 다시 가져갈 수 있어야 합니다.
- 외부 서버가 접수한 직후 응답이 끊기는 경우까지 ‘절대 한 번’을 보장한다고 쓰지 않습니다. 안정적인 알림 ID와 표시 tag 등으로 중복의 영향을 줄이는 정책을 정합니다.

웹 푸시의 접수 응답은 단말 도착을 뜻하지 않습니다. `sent_at`·`last_ok_at`도 무엇이 성공한 시각인지 이름과 설명을 맞춰 주세요. [RFC 8030 §5](https://www.rfc-editor.org/rfc/rfc8030.html#section-5)

### 10분 묶음과 아침 요약의 단위

계획은 ‘같은 회원의 식사 기록은 10분 묶음’, ‘야간 알림은 아침에 하나’라고 하지만, 대기열 병합 키는 `(받는 사람, 종류, 회원)`입니다. 트레이너의 여러 회원·여러 종류가 쌓이면 아침에 여러 행이 생깁니다. 정말 한 번만 보낼 것이라면 별도의 수신자 단위 요약이 필요합니다.

아래를 기본안으로 권합니다. 제품 정책이므로 사용자 선택에 따라 바꿀 수 있습니다.

| 항목 | 권장 기본안 |
|---|---|
| 새 식사 기록 | 첫 기록부터 10분 뒤 한 번. 이후 기록으로 발송 시각을 계속 미루지 않음 |
| 피드백과 질문 | 주간에는 즉시 대기열 처리. 식사 기록용 10분 지연을 일괄 적용하지 않음 |
| 야간 | Asia/Seoul 22:00 이상부터 다음 07:00 전까지 새 발송·재시도를 미룸 |
| 아침 요약 | 수신자별 남은 미확인 소식을 한 알림으로 요약. 여러 회원의 경우 전체 확인 목록 또는 피드백 탭으로 이동 |
| 세는 단위 | 식사 수·질문 수·피드백 사건 수 중 무엇인지 문구와 일치. 평가와 댓글을 함께 남겼을 때의 중복도 정의 |

07:00은 서버가 발송을 시작하는 목표 시각입니다. cron 실행과 외부 전달이 있으므로 휴대폰에 정확히 그 시각에 도착한다고 약속하지 않습니다.

### 발송 직전 취소 조건과 유효기간

현재 계획은 종류별 설정을 대기열에 넣을 때만 확인합니다. 대기하는 동안 사용자가 끄거나 앱에서 이미 내용을 읽을 수 있습니다. **쌓을 때와 보낼 때 모두 확인**해 주세요.

발송 직전에 검사할 조건은 다음과 같습니다.

- 기기 구독과 관련 세션이 유효한지.
- 현재 종류별 설정과 전체 송신 설정이 켜져 있는지.
- 회원이 이미 피드백을 읽었거나 트레이너가 해당 질문·기록을 처리했는지.
- 식사가 삭제됐거나 받는 사람과의 관계가 더 이상 유효하지 않은지.
- 대기열에서 정한 유효기간을 넘겼는지.

현재 [회원 읽음 처리](../../src/member/MemberApp.tsx)와 [미확인 상태 판단](../../src/lib/status.ts)을 알림의 기준과 맞춰 주세요. 상태 검사에 필요한 ID·시각은 읽되, 식단·댓글 원문을 알림 문구 생성에 사용하지 않는 정책을 유지합니다.

대기열 보관 기한과 외부 푸시 서비스에 전달하는 TTL은 구분해서 정합니다. 재시도는 404·410의 구독 종료, 429의 재시도 대기, 일시적 서버·네트워크 실패, 설정·인증 오류를 구분해 처리합니다. 3회 제한만 두고 연속 호출하지 않습니다. TTL과 429의 Retry-After 처리는 웹 푸시 규격에도 나옵니다. [RFC 8030](https://www.rfc-editor.org/rfc/rfc8030.html)

### 기기와 계정 설정의 범위

전체 켜기·끄기는 기기별인데, `notification_prefs(user_id, ...)`는 계정 전체 설정입니다. 이대로라면 한 휴대폰에서 질문 알림을 끄면 같은 계정의 다른 기기에도 적용됩니다.

이 동작을 원하면 화면에 ‘종류별 설정은 모든 기기에 적용’을 표시합니다. 종류별로도 각 기기에서 따로 정하려면 구독 또는 기기 식별자 기준으로 저장 구조를 바꿔야 합니다.

다음 기기 등록 규칙도 정해 주세요.

- `user_id`와 `session_id`는 서버가 현재 인증 정보에서 확정하거나 검증합니다. 클라이언트가 보낸 임의의 세션 ID와 ‘세션이 하나 존재함’만으로 등록을 인정하지 않습니다.
- 같은 브라우저에서 A가 로그아웃하고 B가 로그인할 때 기존 endpoint와 새 소유자의 충돌을 처리합니다. 브라우저에는 기존 구독이 남아 있을 수 있습니다. [MDN 구독 설명](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe)
- 권한 허용, 브라우저 구독 생성, DB 저장, 시험 알림 접수를 각각 구분합니다. DB 저장이 실패했는데 ‘알림을 켰어요’로 끝내지 않습니다.
- 앱 복귀 시 권한·브라우저 구독·서버 등록 상태를 맞춥니다. 앱 삭제나 OS 설정 변경을 서버가 즉시 안다고 가정하지 않습니다.
- 등록 endpoint는 외부 요청 대상이므로 정상 푸시 서비스 주소인지 검증하고 임의 주소·리디렉션으로 서버가 요청하지 않게 합니다. endpoint와 키를 일반 로그에 그대로 남기지 않습니다. endpoint는 비밀로 취급해야 하는 capability URL입니다. [MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)

### 알림 클릭과 작성 중 입력

`?open=` 값만 정해서는 열린 앱과 로그인 대기 상태를 다루기에 부족합니다. 기존 앱에는 작성 중 입력을 보호하는 [isBusy 처리](../../src/lib/appUpdate.ts)가 있습니다.

- 열린 앱이 있으면 창을 활성화하고 메시지로 이동 의도를 전달하는 방식을 우선합니다. 주소로 다시 이동시켜 페이지를 새로고침하면 작성 중 식단·댓글이 사라질 수 있습니다.
- 입력 중이면 그 값을 보존하고 사용자가 알림 화면으로 넘어갈 방법을 제공합니다.
- 앱이 닫혔을 때는 안전한 내부 주소로 열고, 로그인과 프로필 확인이 끝난 뒤 이동 요청을 처리합니다.
- 알림을 받은 계정과 현재 로그인 계정이 다르거나, 삭제·접근 불가 식사이면 이름이나 내용을 노출하지 않고 현재 계정의 기본 화면으로 안내합니다.
- 오래된 식사라도 ID로 권한을 확인해 불러올 수 있어야 합니다. 현재 기본 조회 기간 밖이라는 이유만으로 링크가 깨지지 않게 합니다. [식사 개별 재조회](../../src/components/useMealStore.ts)
- 단일 식사와 여러 식사 요약의 이동 경로를 구분합니다. URL과 메시지는 정해진 종류·ID 형식만 허용하고 외부 주소를 그대로 열지 않습니다.
- 알림 클릭 자체를 피드백 읽음·질문 처리 완료로 취급하지 않습니다. 실제 화면에서 확인한 뒤 기존 상태 처리 규칙을 따릅니다.

### 서버 인증과 비공개 대기열 접근

공유 비밀을 쓰겠다는 방향 외에 실제 호출 경로를 적어 주세요.

- `pg_net`·cron 호출의 인증 방식과 Edge Function의 `verify_jwt` 설정을 맞춥니다. 공유 비밀 머리글을 함수 안에서만 검사한다고 써 두면 기본 JWT 검사에서 먼저 막힐 수 있습니다. Supabase 공식 문서는 서비스 간 호출과 사용자 호출을 구분합니다. [Edge Function 인증](https://supabase.com/docs/guides/functions/auth)
- `private.push_outbox`와 `auth.sessions`를 함수가 어떤 DB 경로로 읽는지 정합니다. 현재 [API 노출 스키마](../../supabase/config.toml)는 `public`, `graphql_public`입니다. 비공개 스키마가 일반 Supabase 클라이언트에서 자동으로 조회된다고 가정하지 않습니다. 발송 전용 권한의 RPC 등을 명시합니다. [Supabase 스키마 노출](https://supabase.com/docs/guides/api/using-custom-schemas)
- 대기열 선점·전송 완료 처리는 일반 회원·트레이너가 호출할 수 없게 합니다. 서비스용 권한은 RLS를 우회할 수 있으므로 함수 내부에서도 수신자·설정·세션을 확인합니다.
- 식단 저장과 대기열 기록은 일관되게 확정하고, 외부 푸시 서버의 장애는 식단 저장을 막지 않게 합니다. 즉시 호출이 실패해도 cron으로 재개할 수 있어야 합니다.

## 먼저 만들 작은 검증과 구현 순서

1. **알림 최소 검증:** HTTPS 시험 환경의 설치 앱에서 허용 → 구독 저장 → 실제 푸시 1건 수신 → 클릭해 열린 앱과 닫힌 앱 각각 진입. Deno 라이브러리·VAPID·서비스워커·함수 인증까지 이어서 확인합니다. 모의 수신 서버만으로 이 완료 기준을 대신하지 않습니다.
2. **사용자·세션·기기 등록:** 재로그인, 계정 전환, 전체 끄기, 세션 종료, 구독 변경·DB 저장 실패를 처리합니다.
3. **단일 알림과 안전한 이동:** 피드백·질문 등 단일 사건부터 수신자·미확인 상태·입력 보존을 확인합니다.
4. **묶음과 야간 처리:** 위 정책을 정한 뒤 대기열 선점·기기별 부분 성공·재시도·아침 요약을 구현합니다.
5. **제한 공개 후 확대:** 기존 업데이트 검증에 더해 구버전에서 푸시 지원 버전으로 넘어가는 경우를 확인합니다. 전체 송신을 즉시 끌 수 있는 설정을 두고, 운영 확대 전에 실제 두 휴대폰으로 확인합니다.

로컬 자동 검증에는 적어도 다음을 추가해 주세요: 동시 발송 호출, 두 기기 중 한 대만 실패, 처리 중 함수 종료, 야간 대기 중 이미 읽음, 대기 중 종류 끄기·로그아웃·계정 되찾기, note 수정, 등록 endpoint 재사용, 작성 중 알림 클릭, 다른 계정으로 알림 열기.

## 사용자에게 받을 결정과 문구

식사 기록을 10분 단위로 묶는 안, 야간 제한, 종류별 설정의 기기·계정 범위는 사용자에게 확인할 제품 선택입니다. 실제 기기 시험 환경·중복 처리·인증 방식은 개발자가 구체화할 구현 항목으로 분리하면 됩니다. 회원 기록 독촉 알림을 이번에 제외하는 방향은 유지할 만합니다.

잠금 화면에 이름을 넣을지도 한 번 정해 주세요. 원문은 넣지 않더라도 닉네임과 식사 시각·종류는 표시되는 정보입니다. 더 적게 드러내려면 기본 문구를 ‘새 피드백이 있어요’, ‘확인할 식사 기록이 있어요’, ‘새 질문이 있어요’로 두고 앱 안에서 이름을 보여 줄 수 있습니다.

첫 안내에서는 ‘알림을 켠 기기에서 받을 수 있어요’로 설명하고, 접수 성공을 실제 도착·열람으로 표현하지 않습니다. 집중 모드·네트워크·OS 설정의 영향을 받을 수 있으므로 ‘놓치는 소식이 없다’는 보장 문구는 바꾸는 편이 좋습니다. [WebKit 집중 모드 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [RFC 접수와 도착의 구분](https://www.rfc-editor.org/rfc/rfc8030.html#section-5)

## 확인 범위

계획 원문, 현재 앱의 서비스워커 설정·업데이트 보호·PIN 변경 및 되찾기 함수·메시지와 읽음 상태 처리를 읽고 공식 문서를 대조했습니다. 푸시 구현은 아직 없으므로 실제 알림 수신이나 부하 시험을 실행한 결과는 아닙니다.
