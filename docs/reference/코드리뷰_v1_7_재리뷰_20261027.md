## 발견 사항

### 1. P2 같은 식사를 다시 평가해도 새 알림 시각이 반영되지 않음

위치: [activity.ts 85행](../../src/lib/activity.ts), [병합 함수 31행](../../src/lib/activity.ts).

`reload()`는 `merge(head, prev)`로 새 첫 페이지와 기존 목록을 합친다. 병합 함수는 같은 key일 때 뒤에 나온 항목을 남기므로 기존 값인 `prev`가 최신 서버 값인 `head`를 덮는다.

SQL의 평가 소식 key는 `rated:식사ID`로 고정이고, 재평가하면 같은 key의 `at`만 바뀐다. 따라서 이미 목록을 받은 상태에서 트레이너가 평가를 바꾸면 서버가 새 시각을 반환해도 화면과 새 소식 판단에는 과거 시각이 계속 쓰인다. SQL에서 현재 상태로 생성하는 소식을 클라이언트가 수정 불가능한 사건처럼 취급하고 있다. 닉네임이나 기록의 한마디 여부처럼 같은 key의 다른 표시 값이 바뀌는 경우도 같은 병합 규칙을 탄다.

실제 `useActivity` 훅 재현:

- 기존 평가: 01시, 마지막 읽음: 02시.
- 재평가 후 서버 응답: 같은 key, 03시.
- 새로 조회한 뒤에도 훅의 시각: 01시, 새 소식 수: 0.

수정 방향: 겹치는 key에는 새로 성공한 조회 값을 반영한다. 단순히 배열 순서만 바꾸는 것으로 아래의 페이지 연속성과 삭제 문제까지 해결되지는 않는다. 같은 key의 시각이 바뀔 때 목록 강조와 읽음 처리가 함께 작동하는지도 확인한다.

검증: 평가 A 조회·읽음 → 다른 기기에서 같은 식사 재평가 B → 앱 복귀 또는 재조회 → B 시각 표시와 새 소식 점. 한마디 유무·닉네임이 바뀐 경우도 갱신 값을 확인한다.

### 2. P2 새 소식이 첫 페이지보다 많이 들어오면 중간 소식을 건너뜀

위치: [activity.ts 85~87행](../../src/lib/activity.ts), [loadMore 93~102행](../../src/lib/activity.ts).

이미 받은 목록을 유지하면서 첫 페이지만 새로 합친 뒤, 더 보기는 합친 목록의 가장 오래된 항목을 커서로 쓴다. 새 첫 페이지와 기존 목록 사이가 이어져 있는지 확인하지 않는다.

재현 순서:

1. 기존 소식 50건을 조회한다.
2. 앱을 보지 않는 사이 더 최신 소식 60건이 생긴다.
3. 앱 복귀 조회는 새 소식 중 최신 50건만 받고, 기존 50건을 붙인다.
4. 더 보기를 누르면 기존 50건의 마지막 항목보다 과거를 조회한다.
5. 그보다 오래된 항목이 없으면 더 보기가 끝난다. 새 소식 중 빠진 10건에는 도달하지 못한다.

실제 훅 재현 결과: 서버 110건, 받은 목록 100건, 누락 10건, `hasMore: false`. 단순한 63건 조회의 50+13 페이지 검증은 통과하지만, 재조회와 페이지 처리가 섞이는 흐름은 해결되지 않았다. 조회 간격은 1분 타이머뿐 아니라 몇 시간 뒤 앱 복귀도 포함한다.

수정 방향: 현재 목록이 서버 정렬 순서상 연속된 범위인지 보장한다. 첫 페이지를 새로 받으면 목록과 커서를 함께 초기화하는 방법이 가장 단순하다. 이미 펼친 목록을 유지하려면 새 페이지와 기존 목록이 연결되는 지점까지 조회하고, 빈 구간의 조회 커서를 별도로 관리해야 한다. 합친 목록의 마지막 항목이 곧 다음 페이지의 안전한 시작점이라고 가정하지 않는다.

검증: 50건 조회 → 60건 추가 → 첫 페이지 갱신 → 더 보기로 총 110건에 모두 도달. 새로 추가한 항목과 이전 페이지가 일부 겹치는 경우, 모든 페이지를 한 번 연 뒤 추가되는 경우도 확인한다.

### 3. P2 삭제되거나 최근 1주일 범위에서 빠진 소식이 계속 남음

위치: [activity.ts 85행](../../src/lib/activity.ts).

첫 페이지를 다시 받아도 이전 항목을 무조건 합치며 제거하지 않는다. 서버가 빈 목록을 돌려줘도 `merge([], prev)`는 과거 목록을 그대로 남긴다. 식사 삭제나 7일 경과로 서버 조회에서 소식이 없어져도, 앱을 계속 열어 둔 기기의 목록과 새 소식 점에는 남을 수 있다. 삭제한 식사를 누르면 볼 수 없다는 안내만 나온다.

실제 훅 재현: 처음 한 건을 조회한 뒤 서버 응답을 빈 목록으로 바꾸고 다시 조회했다. 서버 0건인데 훅에는 1건, 새 소식 수 1이 남았다.

수정 방향: 성공한 재조회는 서버에서 사라진 항목도 반영해야 한다. 특히 첫 페이지가 50건 미만이면 서버의 현재 전체 결과를 받은 것이므로 기존 목록을 계속 덧붙일 이유가 없다. 일부 페이지를 유지하는 경우에도 조회 범위와 서버에서 없어진 항목을 정리하는 정책이 필요하다. 1번의 덮어쓰기 순서만 고쳐서는 해결되지 않는다.

검증: 소식이 있는 식사 삭제 → 재조회 → 목록·점에서 제거. 최근 1주일 경계가 지난 경우에도 제거. 다음 페이지를 펼친 상태의 삭제도 포함한다.

로컬 DB 검증은 새 시험 계정을 만들고 private 상태·가짜 구독·발송 요청을 한 트랜잭션에서 확인한 뒤 롤백했다. 실제 푸시 요청을 전송하지 않았고 시험 계정은 정리했다. 후속 발송은 대기 처리 함수를 직접 호출한 검증이며, cron 실행부터 실기기 도착까지 시간을 측정한 것은 아니다.

## 코드 품질 평가

### 개선된 부분

- `Loaded<T>`로 설정 로딩·실패·성공을 구분하고, 실패와 기본값을 분리했다. 표시 값과 저장 중 값을 나눈 것도 복구 동작을 이해하기 쉽게 한다.
- 변경한 필드만 저장하고 서버 응답으로 화면을 확정한다. 기존 전체 설정 덮어쓰기보다 여러 기기 환경에 맞다.
- `useActivity.reload()`에 기존 useInbody와 같은 요청 번호 보호를 넣었다. 읽음 시각 조회 실패도 ‘아직 안 읽음’과 구분한다.
- `pushOpen.ts`를 분리해 로그아웃의 기기 등록 해제 경로가 React 화면 이동 훅을 포함한 모듈에 의존하지 않게 했다.
- 앞선 네 가지 화면 문제를 회귀 검증으로 추가했다. 서비스워커와 앱의 저장 형식·이동 대상 상수 비교도 추가했다.

### 남은 구조 문제

알림 목록에는 ‘특정 시각의 사건’과 ‘현재 상태를 다시 읽으면 값이 바뀌는 소식’이 섞여 있다. SQL은 평가나 한마디 수정을 같은 key의 최신 값으로 반환하는데, 클라이언트 병합은 과거 값도 계속 맞다고 가정한다. 페이지 커서 역시 연속된 서버 목록을 전제로 하지만 캐시는 서로 떨어진 구간을 연결할 수 있다. 이번 세 결함은 이런 데이터 계약과 갱신 정책의 불일치에서 나온다.

다음 수정에서는 병합 함수를 더 복잡하게 만들기 전에 갱신 단위를 정하는 편이 좋다. 현재 규모에서는 ‘재조회 시 첫 페이지부터 다시 시작’도 합리적이다. 펼친 목록 유지가 꼭 필요하면, 어떤 범위까지 최신으로 확인했는지와 어디부터 더 받아야 하는지를 함께 관리해야 한다. 새 상태 관리 프레임워크를 도입할 필요는 없다.

테스트는 개별 결함의 회귀 확인에서 개선됐지만, **첫 조회 → 데이터 변경 → 재조회 → 다음 페이지**라는 기능 결합 흐름이 빠져 있다. 위 3건을 실제 훅을 쓰는 검증으로 추가하고, 수정 전 코드에서 실패하는지 확인한다. 서비스워커 상수 검증은 문자열 대조이므로 실제 notificationclick → 저장 → 앱 이동의 연동 검증을 대신하지는 않는다.
