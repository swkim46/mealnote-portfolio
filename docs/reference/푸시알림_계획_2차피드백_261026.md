# 푸시 알림 계획 2차 검토

검토일: 2026-10-26  
대상: [수정된 계획](./푸시알림_계획_261026.md)과 현재 앱 코드. 푸시 구현의 실행 결과가 아니라 구현 전 설계 검토다.

## 판단

이전 피드백은 대부분 반영됐다. 운영 배포 전 실제 기기 시험, 일반 PIN 변경과 계정 되찾기 구분, 한마디 수정 포함, 기기별 전송 결과, 설정 범위, 입력 보호, 서버 인증 경로가 구체화됐다.

식사·댓글 저장에 트리거를 추가하지 않고 정기적으로 상태를 조회하는 방식도 이번 알림에 적합하다. 다만 상태 조회 뒤에는 전송 작업과 재시도가 생기므로, 그 구간의 상태 변화까지 없어지는 것은 아니다. 아래 다섯 가지를 구현 규칙과 검증 항목에 추가하면 좋겠다.

사용자가 정한 알림 시각, 야간 제한 없음, 종류별 설정의 계정 전체 적용은 그대로 전제로 삼았다.

## 1. 질문 판정을 현재 앱과 정확히 맞추기

대상: 계획 105행.

계획의 `member_msg_at > trainer_msg_at`만으로는 현재 앱의 질문 판정을 재현할 수 없다. 앱은 마지막 대화가 회원의 말인지와, 그 뒤 트레이너가 `reviewed_at`으로 확인했는지를 함께 본다. [현재 pendingQuestion](../../src/lib/status.ts)

예를 들어 회원이 질문하고 트레이너가 **답변 없이 확인**하면 앱에서는 처리 완료다. 하지만 트레이너 답글 시각은 갱신되지 않으므로, 계획의 비교만 사용하면 이미 처리한 질문을 다시 셀 수 있다. 첫 질문처럼 트레이너 메시지 시각이 NULL인 경우에도 단순 SQL 비교는 질문을 잡지 못한다.

추가할 규칙:

- 질문 건수와 확인할 식사 건수를 각각 현재 `pendingQuestion`·`needsTrainer`와 같은 의미로 계산한다. `reviewed_at`, 마지막 대화의 작성자, NULL 시각을 처리한다.
- ID·시각만 조회하는 원칙은 유지하되, 위 판정에 필요한 작성자 구분과 한마디 유무 등 상태 정보는 조회할 수 있게 설명을 맞춘다. 원문을 푸시 문구에 사용하지 않는다.

검증: 첫 회원 질문, 답변 없이 확인, 확인 후 새 질문, 한마디 수정, 트레이너 답변 후 상태를 각각 화면 판정과 대조한다.

## 2. 재시도 직전에도 이미 읽음·처리·기록 여부 확인하기

대상: 계획 104행, 118~124행.

“상태를 조회하므로 대기 중 이미 읽음은 따로 처리할 필요가 없다”는 설명은 재시도 설계와 맞지 않는다. `push_deliveries`에 작업이 남고 429·서버 오류 뒤에 다시 보내기 때문이다. 현재 발송 직전 검사 목록에는 세션·설정·송신 스위치·만료만 있다.

예를 들어 새 피드백 알림이 429로 미뤄진 사이 회원이 읽으면, 재시도 시점에는 보낼 이유가 없어졌다. 점심 알림을 미룬 사이 점심을 기록한 경우도 같다.

추가할 규칙:

- 최초 발송과 모든 재시도 직전에 해당 알림의 근거가 아직 유효한지 확인한다. 피드백 읽음, 질문·식사 처리, 식사 삭제·담당 관계 변경, 점심·저녁 기록 완료를 반영한다.
- 이미 만든 알림이 어떤 시각까지의 새 소식을 대상으로 하는지 저장한다. 그 알림을 만든 뒤 생긴 새 피드백을 오래된 재시도의 근거로 혼용하지 않는다.
- 근거가 사라지면 전송 작업을 취소한다. 필요하면 요약 건수도 최신 상태로 다시 계산한다.

검증: 429 또는 일시 실패 → 읽음·확인·식사 기록 → 재시도에서 발송되지 않음. 그 뒤 새로 생긴 소식은 다음 알림으로 정상 처리됨.

## 3. 같은 endpoint의 계정 전환 시 예전 전송 작업 끊기

대상: 계획 112행, 118행, 122행.

같은 브라우저에서 계정을 바꾸면 endpoint의 소유자를 바꾸는 방향은 맞다. 다만 구독 ID를 유지하면서 사용자·세션만 바꾸면, 예전 계정의 전송 작업이 그 구독을 계속 참조할 수 있다.

예: A의 알림이 재시도 대기 → 같은 endpoint를 B 계정으로 등록 → B의 새 세션이 유효하다는 검사만 통과 → A의 알림을 B에게 발송. 이름이 없어도 A의 활동 여부나 건수는 다른 계정에 전달된다.

추가할 규칙:

- 계정 전환 때 이전 계정의 미발송 전송 작업을 같은 트랜잭션에서 취소하거나, 새 등록을 별도 구독 ID로 만들어 이전 작업과 분리한다.
- 발송 직전에 `알림.user_id = 구독.user_id = 해당 세션.user_id`를 확인한다. 세션이 단순히 존재하는지만 검사하지 않는다.
- 이미 외부 푸시 서버에 접수된 알림은 회수하지 못한다는 기존 설명은 유지한다.

검증: A의 전송을 429로 대기시킨 뒤 B로 계정을 전환한다. 재시도에서 A 알림이 추가 발송되지 않고, B의 새 알림은 정상 발송되는지 확인한다.

## 4. 전송 선점과 알림 생성의 중복 방지를 구분하기

대상: 계획 121행.

전송 행을 `FOR UPDATE SKIP LOCKED`로 가져오는 것은 이미 있는 같은 작업을 두 함수가 동시에 처리하는 것을 막는다. 하지만 두 함수가 같은 사용자 상태를 읽고 **각각 다른 알림과 전송 행을 만드는 것**까지 막는 규칙은 아직 명시되지 않았다. 상태 갱신과 생성을 같은 트랜잭션에 넣는 것만으로는 충분하다고 볼 수 없다.

추가할 규칙:

- 사용자별 `push_state`를 먼저 잠그고 대상 판단·알림 생성·기준 시각 갱신을 하거나, 사용자·종류·예정 회차를 식별하는 고유 키로 중복 생성을 막는다.
- 전송에는 `(notification_id, subscription_id)` 고유 제약을 둔다.
- `push_state`의 시각이 ‘알림 생성 기준’인지 ‘외부 서버 접수 성공 기준’인지 명시하고, 유효한 구독이 없거나 송신을 껐을 때 기준 시각을 전진시키는지도 정한다.

검증: 두 작업을 같은 시점의 대상 판정에서 겹치게 실행해 알림 생성 수까지 확인한다. 단순히 같은 전송 행을 두 번 가져오지 않는지만 확인하지 않는다.

## 5. 휴대폰 시험 빌드의 DB 연결 경로 확정하기

대상: 계획 146행.

`vite preview`에 `/supabase` 프록시를 추가하는 것만으로는 현재 연결 코드가 그 프록시를 사용하지 않는다. [supabase.ts 10행](../../src/lib/supabase.ts)은 `import.meta.env.DEV`일 때만 로컬 주소를 같은 출처의 `/supabase`로 바꾼다.

일반 `vite build`는 `DEV=false`이며, `vite build --mode development`도 기본적으로 `NODE_ENV=production`이므로 이 조건을 통과하지 않는다. 로컬 DB 주소를 그대로 넣으면 휴대폰이 자기 자신의 `127.0.0.1`로 접속하게 된다. [Vite 공식 환경·모드 설명](https://vite.dev/guide/env-and-mode#node-env-and-modes)

추가할 규칙:

- 시험용 빌드 모드·환경 변수·실행 명령을 정확히 정한다.
- 시험 빌드에서 터널의 `/supabase`를 사용하도록 별도 연결 설정을 하거나, 시험용 URL을 터널의 완전한 HTTPS 주소로 지정한다. `preview.proxy` 추가만으로 끝내지 않는다.
- 시험 실행 전 DB 대상이 로컬인지 확인하고 운영 주소가 섞이면 중단한다. 이 검사는 키 원문을 로그에 남기지 않고 수행한다.

검증: 실제 휴대폰의 식단 조회·저장이 터널을 통해 로컬 DB로만 가고, 서비스워커가 활성화된 상태에서 실제 푸시 수신까지 이어지는지 확인한다.

## 짧게 추가하면 좋은 명세

- **닫힌 앱에서 계정 구분:** 현재 `/?open=feedback` 같은 주소에는 알림 수신 계정 정보가 없다. 알림 ID·수신 계정·화면 종류를 어떤 방식으로 보존해 로그인 완료 뒤 비교할지 정한다. 열린 창의 `postMessage`와 닫힌 앱의 최초 실행 양쪽을 포함한다.
- **운영에서 송신 스위치를 끈 상태의 시험:** 시험 계정만 허용하는 경로 등, 전체 발송을 켜지 않고 두 휴대폰으로 확인할 방법을 정한다.
- **설정 문구:** 실제 시각이 9·15·21시라면 ‘6시간마다’보다 ‘하루 3회(9·15·21시)’가 정확하다. 다른 선택도 ‘하루 5회(9·12·15·18·21시)’로 쓸 수 있다. 정해 둔 발송 시각을 바꾸자는 뜻은 아니다.

앱 코드와 계획 원문은 수정하지 않았다. 이번 검토에서 실제 푸시 수신 시험은 실행하지 않았다.
