# v1.7 dev 코드 품질 추가 리뷰

후속 확인 결과는 [최신 재리뷰](./코드리뷰_v1_7_재리뷰_20261027.md)에 정리했다. 아래는 수정 전 평가와 재현 기록이다.

대상은 `app/`의 dev 작업 파일이다. 기준 커밋은 `51de16b`이며, 미커밋 푸시 알림·알림 목록 기능을 기존 코드와 함께 검토했다. 앞선 동작 리뷰(이 저장소에 미포함)의 3건과 별개로, 아래 4건을 추가 재현했다. 앞으로의 리뷰에는 [코드 리뷰 평가 기준](./코드리뷰_평가기준.md)을 적용한다.

현재 변경은 기존 구조를 전부 무시한 코드는 아니다. 설정·목록 UI를 별도 컴포넌트로 뒀고, 기존 Sheet와 계정 화면을 활용했다. 푸시 클릭은 작성 중인 시트를 유지하며, 기존 서비스워커 업데이트 흐름도 보존하도록 연결했다. 그러나 기존 코드에서 이미 다뤘던 조회 실패와 늦은 응답 처리가 새 화면에는 일관되게 적용되지 않았다. 정상 동작을 추가한 뒤 실패·경쟁 상황의 처리가 별도로 남은 상태다.

## 추가로 확인한 결함

### 1. P2 설정 조회 실패가 기본값으로 바뀌어 기존 설정을 덮어씀

위치: [PushSettings.tsx 23~29행](../../src/components/PushSettings.tsx), [push.ts 107행](../../src/lib/push.ts).

`fetchPrefs()`는 정상적으로 조회했지만 행이 없을 때만 기본값을 반환하고, 조회 오류는 던진다. 그런데 화면이 이 오류를 다시 `DEFAULT_PREFS`로 바꾼다. 그 결과 서버 값을 모르는 상태에서 모든 알림이 켜진 것으로 표시되고, 하나를 바꾸면 전체 설정을 upsert한다. 예를 들어 피드백 알림을 꺼 둔 사용자가 조회 실패 후 식단 기록 알림만 끄면, 피드백 알림은 의도와 다르게 켜진 값으로 저장된다. 종류 설정은 계정 전체에 적용되므로 다른 기기에도 영향을 준다.

재현: 실제 PushSettings 컴포넌트의 설정 조회만 실패시킨 뒤 식단 기록 알림을 해제했다. 피드백을 변경하지 않았는데 저장 요청에는 `feedback: true`가 포함됐다.

수정 방향: 설정의 로딩·조회 실패·조회 성공을 구분하고, 실패하면 다시 받기와 안내를 보여 준다. 서버 값을 확인하기 전에는 종류 설정 저장을 허용하지 않는다. 같은 effect의 `deviceState()` 실패를 `'off'`로 바꾸는 부분도 확인 실패와 실제 꺼짐을 구분한다.

품질 관점: 데이터 계층에서 구분한 오류를 화면에서 없애고 있다. 기존 `useInbody`와 App의 프로필 조회는 실패 상태를 별도로 표현한다. 새 화면도 같은 원칙을 따라야 한다.

### 2. P2 설정 연속 저장이 역순으로 끝나면 화면과 서버가 달라짐

위치: [PushSettings.tsx 65~74행](../../src/components/PushSettings.tsx), [push.ts 107행](../../src/lib/push.ts).

토글마다 전체 설정의 사본을 독립적으로 저장하며, 저장 중에도 다른 토글을 조작할 수 있다. 피드백 알림 끄기 A → 식단 기록 알림 끄기 B를 빠르게 누르고 B가 먼저 완료되면, 나중에 끝나는 A가 B의 변경을 되돌린다. 화면은 두 항목이 모두 꺼져 있지만 서버에는 식단 기록 알림이 켜져 남는다. 오래된 요청의 실패가 최신 화면 상태까지 되돌리는 구조도 같은 함수에 있다.

재현: 실제 컴포넌트에서 두 토글을 끄고 저장 응답·서버 반영 순서를 B → A로 제어했다. 최종 화면 `reminder: false`, 서버 모형 `reminder: true`로 달랐다.

수정 방향: 이 작은 설정 화면에서는 저장 중 조작을 막고 결과를 확정하는 방법부터 검토할 수 있다. 연속 조작을 지원한다면 저장을 순서대로 처리하고 최신 의도를 보존한다. 여러 기기에서 서로 다른 설정을 바꾸는 경우까지 고려하면 변경한 필드만 저장하는 방식도 필요하다. 이전 요청의 실패로 최신 성공 상태를 되돌리지 않는다.

품질 관점: 낙관적 화면 변경과 서버 저장을 연결하는 정책이 없다. 클릭마다 async 함수를 추가하는 방식으로는 해결되지 않으며, 한 설정 묶음의 변경 순서를 누가 책임지는지 정해야 한다.

### 3. P2 알림 목록을 못 불러와도 읽음 처리함

위치: [Activity.tsx 9~17행](../../src/components/Activity.tsx).

컴포넌트가 마운트되는 즉시 `markSeen()`을 호출하고, 그 뒤에 로딩·오류 여부를 확인한다. 목록 조회가 실패해서 소식을 하나도 보여 주지 못해도 서버 읽음 시각은 갱신된다. 다음에 정상 조회하면 그 소식은 새 소식이 아닌 것으로 처리된다. 초기 목록이 아직 없을 때의 `fresh` 사본도 빈 집합으로 고정돼 나중에 도착한 소식의 강조가 사라진다.

재현: 목록 조회를 실패시킨 상태에서 목록을 열었다. 오류 안내만 표시됐는데 `mark_activity_seen` 호출은 1회 발생했다. 이 재현은 읽음 호출을 확인한 것이며 실제 DB를 변경하지 않았다.

수정 방향: 성공적으로 받은 목록을 기준으로 새 소식 표시와 읽음을 함께 결정한다. 조회 실패 시에는 읽음 기준을 앞으로 옮기지 않는다. 앞선 리뷰의 페이지 처리와도 연결해, 아직 보여 주지 않은 소식까지 읽은 것으로 간주하지 않도록 읽음 범위를 정한다.

품질 관점: 화면을 열었다는 UI 사건과 사용자가 소식을 확인했다는 업무 처리가 너무 일찍 연결돼 있다. 빈 의존성 배열이나 lint 예외 자체가 문제가 아니라, 마운트 시점에는 필요한 데이터가 준비돼 있다는 가정이 문제다.

### 4. P2 늦은 조회 응답이 읽음 상태를 되돌림

위치: [activity.ts 41~52행](../../src/lib/activity.ts).

초기·주기·화면 복귀 조회와 읽음 저장 뒤 조회가 겹칠 수 있지만, 응답 순서 검사가 없다. 과거 읽음 시각을 받은 조회 A가 지연된 사이 읽음 저장과 최신 조회 B가 끝나면 점이 사라진다. 이후 A가 완료되면 과거 시각으로 덮여 점이 다시 켜진다.

재현: 실제 useActivity 훅에서 A를 지연하고 읽음 저장과 B를 먼저 완료했다. 새 소식 수는 `1 → 0 → 1`로 되돌아갔다.

수정 방향: 현재 데이터에 적용할 수 있는 조회인지 확인한다. 기존 [useInbody.ts](../../src/components/useInbody.ts)의 요청 번호 검사가 참고가 된다. 읽음 시각 조회인 `seen.error`도 검사해, 조회 실패를 ‘한 번도 읽지 않음’으로 바꾸지 않는다. 이 누락은 코드에서 확인했으며 위 경쟁 상황과는 별도다.

품질 관점: 기존에 발견하고 해결한 비동기 문제의 방어 방식이 새 기능에 반영되지 않았다. 반드시 공통 훅으로 추출할 필요는 없지만, 같은 위험에는 같은 보호 원칙을 적용해야 한다.

## 구조와 테스트 평가

### 이번 수정에 함께 정리할 부분

- **실패와 기본값의 구분:** 설정과 읽음 조회에서 공통으로 무너진 부분이다. 분기 몇 개를 덧붙이기 전에 각 데이터의 로딩·실패·성공 상태와 편집 가능 시점을 정한다.
- **조회와 저장의 순서:** 조회는 최신 응답 보호, 저장은 요청 순서와 실패 복구를 각각 다룬다. 조회 응답에 번호만 붙인다고 서버의 역순 저장까지 해결되지는 않는다.
- **알림의 의미:** 앞선 리뷰의 오래된 재시도 부활도 같은 식사와 특정 피드백을 구분하지 못해서 생겼다. 읽음과 취소 판단이 무엇을 기준으로 하는지 먼저 확정한 뒤 조건을 고친다. 알림 목록과 푸시 전송 작업은 용도가 다르므로 무조건 하나의 테이블로 합칠 필요는 없다.

### 후속 개선으로 권하는 부분

[push.ts](../../src/lib/push.ts)는 기기 구독, 설정 API, IndexedDB, React 이동 훅을 함께 맡는다. 로그아웃 경로도 이 모듈에 의존한다. 현재 185행이라는 길이만으로 분리가 필수인 것은 아니지만, 기기 등록·해제와 알림 클릭 처리의 변경 이유는 다르다. 관련 수정 때 기기 구독 API와 `usePushOpen`의 경계를 나누면 인증 코드가 화면 이동·React 훅까지 포함한 모듈을 알 필요가 줄어든다. 이를 위해 큰 상태 관리 도구를 새로 도입할 필요는 없다.

앱과 [push-sw.js](../../public/push-sw.js)는 이동 화면 목록, IndexedDB 이름·버전·저장소·키를 각각 알고 있다. 별도 실행 환경이라 코드가 나뉘는 것은 자연스럽다. 다만 이 값들을 변경할 때 양쪽을 함께 확인할 수 있는 계약 검증은 필요하다. 공유 코드나 빌드 구조를 크게 바꾸기보다 실제 워커가 저장한 값을 앱이 읽는 작은 연동 검증부터 추가하는 편이 적절하다.

### 테스트 평가

기존 권한 검증과 화면 흐름 검증은 정상 기능, 계정 범위, 기본 이동을 확인하는 데 유용하다. 그러나 알림 목록 테스트는 점이 나타날 때까지 기다린 뒤 여는 흐름이라, 데이터가 준비되기 전에 여는 경우를 놓친다. 설정 토글을 순서대로 완료시키는 시험도 역순 저장을 잡지 못한다. 테스트 개수보다 이런 경계의 포함 여부를 봐야 한다.

우선 추가할 회귀 검증은 설정 조회 실패 후 저장, 연속 저장의 역순 완료와 실패, 목록 초기 조회 지연·실패 중 열기, 읽음 저장 전후 조회의 역순 완료다. 앞선 3건의 피드백 재시도·연속 발송·60건 초과 검증도 유지한다. 수정 후에는 고치기 전 코드에서 해당 검증이 실패하는지 확인해야 한다.

## 재현 자료와 확인 범위

프로젝트 내부 ignore 경로에 실행 스크립트(`scripts/review-local/quality-20261027.mjs`, 이 저장소에 미포함), 실제 컴포넌트 연결부(`scripts/review-local/quality-20261027.tsx`, 이 저장소에 미포함), HTML 진입 파일을 보관했다. Playwright로 실제 컴포넌트·훅을 실행하고 서버 응답만 제어했다. 운영, 실제 DB, 실제 푸시 전송은 사용하지 않았다. 앱 구현 파일은 수정하지 않았다.

`app/`에서 실행:

```sh
node scripts/review-local/quality-20261027.mjs
```

최종 출력:

```json
{"case":"prefs_read_failure","previous_server_feedback":false,"saved_feedback_after_changing_only_reminder":true}
{"case":"prefs_reverse_completion","ui_reminder":false,"server_reminder":true}
{"case":"failed_list_marked_seen","displayed_items":0,"mark_seen_calls":1}
{"case":"activity_stale_read","after_mark_seen":0,"after_older_read_finishes":1}
```

4개 상황 모두 현재 코드의 문제 동작이 재현됐다. 전체 기존 검증이나 실기기 수신 시험의 통과를 의미하지 않는다. 앞선 리뷰의 3건은 이번 실행에서 다시 시험하지 않았다.
