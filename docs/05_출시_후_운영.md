# 쓰는 사람의 기록을 지키며 업데이트하기

[식단노트](../README.md) / 설계 기록 5

10월 20일 처음 배포하고 23일부터 트레이너와 제가 사용하기 시작했습니다. 이후에는 앱을 개발하는 동안에도 회원의 식사 기록과 트레이너의 답변이 쌓였습니다. 새 버전을 내보낼 때 작성 중인 글을 지키고, 개발·검증 과정이 실제 기록을 건드리지 않게 운영 환경을 나눴습니다.

제가 정한 것은 출시 시점과 버전 기준입니다. 업데이트 보호와 배포 검사는 Claude Code가 구현하고, Codex가 검토에서 찾은 예외를 반영하며 보강했습니다. 아래는 v1.7.2까지 운영에 반영한 내용입니다. 실행 명령은 [운영 안내](운영_안내.md)에 있습니다.

## 입력 중인 글을 지키는 자동 업데이트

새 버전을 적용하려고 화면을 다시 불러오면 회원이 쓰던 기록이나 트레이너의 한마디가 사라질 수 있습니다. 현재는 입력이 남아 있으면 자동 적용을 미루고, 직접 적용할 수도 있게 했습니다.

v1.4(10월 23일 개발, 26일 운영)부터 새 버전을 자동으로 적용합니다. 앱으로 돌아올 때와 켜 둔 동안 30분마다 확인하고, 입력 중이 아니면 조용히 바꾸며, 입력 중이면 '지금 적용' 띠를 띄운 뒤 다음에 돌아올 때 바꿉니다([`appUpdate.ts`](../src/lib/appUpdate.ts#L39-L74)).

첫 구현에서 입력 중인지를 확인하는 것만으로는 충분하지 않았습니다. 로그인 연장을 기다리는 동안 쓰기 시작하거나 다른 탭에서 업데이트하면 확인을 거치지 않는 경로가 남아 있었습니다. Codex가 이런 상황을 재현했고, 모든 새로고침 직전에 입력 상태를 다시 확인하는 방식으로 보강했습니다.

새 버전 적용 검증은 실제 빌드 두 개를 번갈아 띄워 확인합니다([`update-check.mjs`](../scripts/update-check.mjs)).

v1.3.1까지는 다른 방식(자동 갱신)이라 새 버전을 바로 넘겨받지 못했습니다. 그래서 v1.4.0으로 올릴 때 기존 사용자는 앱을 한 번 완전히 닫았다 열어야 했습니다.

## 개발 환경과 운영 환경 분리

- 10월 20일부터 개발 DB는 맥 안의 로컬 Supabase로 두고 운영 DB와 나눴습니다. Supabase 무료 플랜의 프로젝트 수가 적어, 개발용 프로젝트를 따로 만들지 않기 위해서입니다([변경 기록](../CHANGELOG.md) 10월 20일).
- 10월 21일 저장소를 만들며 `dev`(작업)와 `main`(운영) 브랜치를 나눴습니다. 개발 서버 화면 위쪽에는 '테스트 환경' 띠가 붙고 운영 빌드에는 들어가지 않습니다.
- 운영 테스트 계정 두 개는 표시를 달아 실제 회원의 가입 화면과 트레이너 목록에 나오지 않게 했습니다.

## 버전과 배포 규칙

**배포한 버전을 기준으로 번호를 매깁니다.** 앱 버전은 N.M.L로 매기고, 업데이트 소식은 N이나 M이 오를 때만 씁니다(10월 21일 제 결정). 10월 23일에는 번호를 운영 배포 기준으로 바꿨습니다. 개발 중에 기능을 여러 번 더해도 운영 버전 번호는 하나로 두고, 개발 단계마다 `v1.4.0-dev.N` 태그를 붙입니다.

배포 명령은 마지막 운영 태그의 바로 다음 번호만 허용합니다([`deploy.sh`](../scripts/deploy.sh#L45-L69)). dev 태그로 그 시점의 코드와 로컬 DB를 되돌리는 스크립트도 만들었고, 실제로 한 단계 되돌리는 시험을 통과했습니다([`dev-rollback.sh`](../scripts/dev-rollback.sh)).

**배포할 코드와 DB가 준비됐는지 확인합니다.** 배포 명령은 `main`이 아니거나, 커밋하지 않은 변경이 있거나, 운영 DB에 적용하지 않은 마이그레이션이 있으면 멈춥니다([`deploy.sh`](../scripts/deploy.sh#L6-L43)). 처음에는 마이그레이션 조회 명령이 실패해 빈 결과가 오면 '0건'으로 읽고 배포가 진행됐는데, Codex 리뷰 지적으로 조회 실패와 응답 형식 이상을 모두 중단으로 바꿨습니다.

v1.7.1부터는 앱과 서버 기능을 같은 커밋으로 함께 올립니다. 앱과 알림 서버 기능이 같은 기본 문구 파일을 쓰는데, 앱만 나가고 알림 문구가 옛것으로 남을 수 있다는 Codex의 배포 후 리뷰를 반영했습니다([`deploy.sh`](../scripts/deploy.sh#L73-L98)).

## 한계

- 자동 배포 파이프라인(CI)은 없습니다. 검증과 배포는 맥에서 명령으로 실행합니다.
- 아이폰 브라우저 엔진(WebKit)에서 인바디 사진 한 장 인식에 140～290초가 걸리는 것(크롬 계열은 3～8초)을 확인했지만 원인은 찾지 못했습니다.

10월 28일에는 v1.8을 테스트 환경에서 개발 중입니다. 이 문서와 공개 코드는 운영에 반영한 v1.7.2를 기준으로 했으며, 후속 구상은 [앞으로의 계획](07_앞으로의_계획.md)에 따로 정리했습니다.
