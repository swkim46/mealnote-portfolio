# 가입과 계정 보안

[식단노트](../README.md) / 설계 기록 3

이 문서는 연락처 없이 가입하게 만든 방식과, PIN을 잊었을 때의 처리를 한 번 바꾼 경위를 정리합니다.

## 연락처를 받지 않는 가입

기획안 v1.2(10월 20일)에서 가입은 닉네임과 숫자 6자리 PIN만 받도록 정했습니다. 이메일과 전화번호는 받지 않습니다([기획안 v1.2](reference/식단관리앱_개발기획안_v1_2.md)).

- 트레이너는 운영자가 나눠 준 등록 코드로 먼저 가입합니다. DB에는 코드 원문이 아니라 해시만 저장합니다.
- 회원은 가입할 때 트레이너 목록에서 담당 트레이너를 고릅니다.
- 로그인은 Supabase의 이메일·비밀번호 방식을 그대로 쓰되, 이메일 자리에 닉네임 해시로 만든 내부 주소를 넣습니다. 메일은 보내지 않습니다([`auth.ts`](../src/lib/auth.ts#L11-L12)).
- 회원은 자기 기록만, 트레이너는 담당 회원의 기록만 읽습니다. 이 범위는 화면이 아니라 DB의 행 단위 권한 규칙으로 막습니다.

## PIN 분실 처리를 바꾼 경위

**v1.2의 방식** — 기획안 v1.2는 PIN을 잊으면 운영자가 관리 화면에서 재설정하는 것을 기본값으로 두었습니다. v1.2 앱(10월 21일)에서는 회원이 로그인 화면에서 요청하면 담당 트레이너가 새 PIN을 만들어 알려 주게 했습니다.

**문제** — Codex 리뷰는 이 방식이 가장 심각한 등급(P1)의 문제라고 지적했습니다. 트레이너가 새 PIN을 만들 수 있으면 회원 몰래 그 계정으로 로그인할 수 있기 때문입니다. 이 지적이 왔을 때 운영에는 이미 v1.2가 나가 있었습니다.

**v1.3의 방식** — 트레이너 재설정을 없애고, 계정을 되찾는 일을 회원 본인만 할 수 있게 바꿨습니다.

- 가입할 때 취향 질문 6개 가운데 하나를 골라 답을 정합니다. 답은 해시로만 저장합니다.
- PIN을 잊으면 그 질문에 답해 바로 새 PIN을 정합니다. 5번 틀리면 24시간 잠기고, 로그인해 둔 기기에 틀린 시도를 알립니다.
- PIN이 바뀌면 로그인해 둔 다른 기기에 알림이 뜹니다. '제가 바꾼 게 아니에요'를 누르면, 바뀌기 전부터 로그인돼 있던 기기에서만 새 PIN과 새 복구 질문으로 계정을 되찾고 다른 기기는 로그아웃됩니다.
- 운영자 화면에 신고·되찾기·잠김 기록이 남습니다. 운영자도 PIN을 만들어 줄 수 없고, 예외 상황에서만 DB에서 직접 바꿉니다([운영 안내](운영_안내.md#운영-작업)).

v1.3은 같은 날 Codex 재검토를 네 번 더 거친 뒤 운영에 나갔습니다.

| 차수 | 지적 | 바꾼 것(요약) |
|---|---|---|
| 1차 | 6건 | 인증 서버의 사용자 정보에 남던 복구 답·등록 코드 원문 삭제, 표준 인증 API로 PIN을 바꾸는 경로 차단, 로그아웃 등으로 세션이 끝난 뒤 남은 로그인 정보로는 데이터에 접근하지 못하게 하는 권한 규칙 추가 |
| 2차 | 3건 | 계정 되찾기의 기준 시각을 언제 열고 옮기는지 정리 |
| 3차 | 3건 | 가입 때 등록 코드와 복구 답을 인증 서버에 보내지 않는 '가입권' 방식, 되찾기를 계정 단위 잠금 안에서 다시 확인 |
| 4차 | 2건 | 되찾기 중에 기다리던 공격자의 변경 차단. 요청을 실제로 동시에 겹쳐 보는 경쟁 상황 검증 추가 |

세부는 [변경 기록](../CHANGELOG.md)의 10월 21일 'v1.3 보안 보강' 1～4차에 있습니다.

## 운영 반영 직후의 점검

v1.3.0을 운영에 반영한 직후 Supabase의 보안 점검에서, 로그인한 사람만 쓰는 함수에 로그인 전 역할(`anon`)의 실행 권한이 남아 있는 것을 발견했습니다. 각 함수가 안에서 로그인과 세션을 확인해 거부하므로 실제 노출은 없었지만, 이중 장치로 그 권한을 거뒀습니다([`20261021000012_revoke_anon_execute.sql`](../supabase/migrations/20261021000012_revoke_anon_execute.sql#L1-L4)). v1.4.0을 반영할 때도 로그인 전에 호출할 수 있는 함수가 기존 다섯 개 그대로인지 확인했습니다.

## 개인정보를 남기지 않는 다른 장치

- 인바디 결과지는 휴대폰 안에서 측정일·체중·골격근량·체지방률만 읽고 사진은 저장하거나 전송하지 않습니다. 인바디 기록 테이블에는 사진 칸이 없습니다(v1.4).
- 앱 의견 보내기는 익명이고, 의견 테이블에는 작성자 칸이 없습니다. 운영자는 의견과 보안 기록만 보고 식단과 회원 기록은 보지 못합니다.
- 잠금 화면 알림에는 이름과 식단 내용을 쓰지 않습니다([알림 설계](04_알림_설계.md)).
- 닉네임은 로그인 아이디를 겸하므로, 닉네임을 바꾸는 서버 함수가 화면 닉네임·로그인 내부 주소·인증 정보를 한 번에 바꿉니다(v1.6).

## 확인한 것

- 권한 검증은 역할별로 읽고 쓸 수 있는 범위, 거부 사유, 가입·복구·되찾기를 확인합니다([`backend-check.mjs`](../scripts/backend-check.mjs)). 10월 21일 이 검증이 '거부됨'만 보고 거부 이유와 성공 경로를 보지 않아, 트레이너의 확인 완료 함수가 항상 실패하던 결함을 놓친 적이 있습니다. 그 뒤 거부 사유 일치와 성공 경로를 함께 검사하게 했습니다.
- 경쟁 상황 검증은 DB 행 잠금으로 요청을 실제로 겹친 뒤, 동시에 들어온 되찾기 요청 가운데 하나만 성공하는지와 되찾기 중에 기다리던 다른 요청의 PIN 변경이 거부되는지 확인합니다([`race-check.mjs`](../scripts/race-check.mjs#L78-L96)). 이 검증은 Codex 재검토가 재현한 상황을 옮긴 것입니다.

## 한계

- 복구 질문의 답을 잊고 로그인해 둔 기기도 없으면 계정을 되찾을 수 없어 새로 가입해야 합니다.
- PIN이 숫자 6자리라 Supabase 보안 점검이 권하는 '유출된 비밀번호 차단' 기능은 맞지 않아 켜지 않았습니다.
