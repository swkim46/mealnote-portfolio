# 가입은 간단하게, 계정 복구는 본인이

[식단노트](../README.md) / 설계 기록 3

회원에게 이메일과 전화번호를 받지 않기로 했으므로, PIN을 잊었을 때도 연락처 인증 없이 계정을 되찾을 방법이 필요했습니다. 처음에는 트레이너가 새 PIN을 정해 줬습니다. Codex가 이 방식의 문제를 지적하고 대안을 제시한 뒤, 제가 회원 본인이 복구하는 절차를 기획했습니다.

## 처음에는 트레이너가 PIN을 다시 정해 줬습니다

[기획안 v1.2](reference/식단관리앱_개발기획안_v1_2.md)는 PIN을 잊으면 운영자가 관리 화면에서 다시 정해 주는 방식을 기본값으로 뒀습니다. v1.2 앱에서는 회원이 요청하면 담당 트레이너가 새 PIN을 만들어 알려주게 했습니다.

Codex는 트레이너가 새 PIN을 정할 수 있으면 회원 몰래 그 계정으로 로그인할 수도 있다고 지적했습니다. 저는 이 지적과 Codex의 아이디어를 보고 복구 절차를 다시 기획했습니다. 연락처를 받지 않는 가입 방식은 유지하되, 앱에서 다른 사람이 회원의 PIN을 대신 정하는 권한을 없애기로 했습니다.

## PIN을 잊었을 때와 다른 사람이 바꿨을 때를 함께 다뤘습니다

복구 질문과 답을 가입할 때 정해 두고, PIN을 잊으면 그 질문에 답해 새 PIN을 정하는 방식으로 기획했습니다. 질문도 직접 기준을 정했습니다. 개인정보를 묻거나 식단 기록으로 짐작할 수 있는 질문을 피하고, 좋아하는 영화·노래처럼 취향에 관한 질문을 골랐습니다([질문 목록](../src/lib/recovery.ts#L1-L10)).

다른 사람이 PIN을 바꿨을 때는 기존에 로그인해 둔 기기로 알리고, 본인이 한 변경이 아니면 그 기기에서 계정을 되찾는 절차를 함께 뒀습니다.

이 기획의 구현은 Claude Code에, 복구 절차의 허점과 예외 상황 검토는 Codex에 맡겼습니다. v1.3에 반영했고, 트레이너의 PIN 재설정 기능은 없앴습니다.

현재 복구 절차는 다음과 같습니다.

- 가입할 때 취향 질문 6개 가운데 하나를 골라 답을 정합니다. 답은 해시로만 저장합니다.
- PIN을 잊으면 그 질문에 답해 바로 새 PIN을 정합니다. 5번 틀리면 24시간 잠기고, 로그인해 둔 기기에 틀린 시도를 알립니다.
- PIN이 바뀌면 로그인해 둔 다른 기기에 알림이 뜹니다. '제가 바꾼 게 아니에요'를 누르면, 바뀌기 전부터 로그인돼 있던 기기에서만 새 PIN과 새 복구 질문으로 계정을 되찾고 다른 기기는 로그아웃됩니다.
- 운영자 화면에 신고·되찾기·잠김 기록이 남습니다. 운영자도 PIN을 만들어 줄 수 없고, 예외 상황에서만 DB에서 직접 바꿉니다([운영 안내](운영_안내.md#운영-작업)).

앱에서 계정을 되찾는 주체는 회원이지만, 복구 질문의 답을 잊고 로그인해 둔 기기도 없으면 직접 되찾을 수 없습니다. 이 경우 새로 가입해야 한다는 한계가 남습니다.

## 계정 복구를 구현하며 확인한 예외

v1.3은 Codex 재검토를 거친 뒤 운영에 나갔습니다.

| 차수 | 지적 | 바꾼 것(요약) |
|---|---|---|
| 1차 | 6건 | 인증 서버의 사용자 정보에 남던 복구 답·등록 코드 원문 삭제, 표준 인증 API로 PIN을 바꾸는 경로 차단, 로그아웃 등으로 세션이 끝난 뒤 남은 로그인 정보로는 데이터에 접근하지 못하게 하는 권한 규칙 추가 |
| 2차 | 3건 | 계정 되찾기의 기준 시각을 언제 열고 옮기는지 정리 |
| 3차 | 3건 | 가입 때 등록 코드와 복구 답을 인증 서버에 보내지 않는 '가입권' 방식, 되찾기를 계정 단위 잠금 안에서 다시 확인 |
| 4차 | 2건 | 되찾기 중에 기다리던 공격자의 변경 차단. 요청을 실제로 동시에 겹쳐 보는 경쟁 상황 검증 추가 |

세부는 [변경 기록](../CHANGELOG.md)의 'v1.3 보안 보강' 1～4차에 있습니다.

## 운영 반영 직후의 점검

v1.3.0을 운영에 반영한 직후 Supabase의 보안 점검에서, 로그인한 사람만 쓰는 함수에 로그인 전 역할(`anon`)의 실행 권한이 남아 있는 것을 발견했습니다. 함수 내부에서 로그인과 세션을 확인해 요청을 거부하고 있었지만, 호출 권한도 거뒀습니다([`20261021000012_revoke_anon_execute.sql`](../supabase/migrations/20261021000012_revoke_anon_execute.sql#L1-L4)).

v1.4.0을 반영할 때도 로그인 전에 호출할 수 있는 함수가 기존 다섯 개 그대로인지 확인했습니다.

## 기록을 볼 수 있는 사람과 남기는 정보를 제한합니다

- 회원은 자기 기록만, 트레이너는 담당 회원의 기록만 읽습니다. DB의 행 단위 권한 규칙으로 이 범위를 제한합니다.
- 인바디 결과지는 휴대폰 안에서 측정일·체중·골격근량·체지방률만 읽고 사진은 저장하거나 전송하지 않습니다. 인바디 기록 테이블에는 사진 칸이 없습니다(v1.4).
- 앱 의견 보내기는 익명이고, 의견 테이블에는 작성자 칸이 없습니다. 운영자는 의견과 보안 기록만 보고 식단과 회원 기록은 보지 못합니다.
- 잠금 화면 알림에는 이름과 식단 내용을 쓰지 않습니다([알림 설계](04_알림_설계.md)).
- 닉네임은 로그인 아이디를 겸하므로, 닉네임을 바꾸는 서버 함수가 화면 닉네임·로그인 내부 주소·인증 정보를 한 번에 바꿉니다(v1.6).

## 가입 구현과 검증 근거

트레이너는 운영자가 나눠 준 등록 코드로 먼저 가입하고, 회원은 가입할 때 담당 트레이너를 고릅니다. DB에는 등록 코드 원문 대신 해시를 저장합니다.

로그인은 Supabase의 이메일·비밀번호 기능을 사용하되, 이메일 자리에 닉네임 해시로 만든 내부 주소를 넣습니다. 회원에게 이메일을 받거나 메일을 보내지는 않습니다([`auth.ts`](../src/lib/auth.ts#L11-L12)).

검증에서는 아래 동작을 확인합니다.

- 권한 검증은 역할별로 읽고 쓸 수 있는 범위, 거부 사유, 가입·복구·되찾기를 확인합니다([`backend-check.mjs`](../scripts/backend-check.mjs)). 초기 검증이 '거부됨'만 보고 거부 이유와 성공 경로를 보지 않아, 트레이너의 확인 완료 함수가 항상 실패하던 결함을 놓친 적이 있습니다. 그 뒤 거부 사유 일치와 성공 경로를 함께 검사하게 했습니다.
- 경쟁 상황 검증은 DB 행 잠금으로 요청을 실제로 겹친 뒤, 동시에 들어온 되찾기 요청 가운데 하나만 성공하는지와 되찾기 중에 기다리던 다른 요청의 PIN 변경이 거부되는지 확인합니다([`race-check.mjs`](../scripts/race-check.mjs#L78-L96)). 이 검증은 Codex 재검토가 재현한 상황을 옮긴 것입니다.

PIN이 숫자 6자리라 Supabase 보안 점검이 권하는 ‘유출된 비밀번호 차단’ 기능은 켜지 않았습니다. 이 제약과 복구 불가 상황까지 포함해 현재 가입 방식의 한계로 남겨 두었습니다.
